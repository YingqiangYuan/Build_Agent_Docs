# 03 — Elevation Roadmap

> **Scope note.** This is a *skills* repo — its "maturity gaps" are not the usual
> web-app gaps (no perf, no data layer, no auth). They are: **can you trust the
> skills without running them by hand? can you tell when upstream docs drift? how
> far does the pattern scale?** The roadmap below is honest: the architecture is
> genuinely strong (the three-layer generator pattern is the hard part and it's
> done), so most upgrades are about *verification, drift-detection, and reach*,
> not rescuing a broken design.

## Executive view — highest-leverage upgrades, in priority order

1. **Automated verification of the doc experts.** Today the only test is manual
   Q&A (`examples/02`). A fixture-backed test suite is the single biggest
   credibility upgrade.
2. **Drift detection / observability.** The whole promise is "never stale" — but
   nothing *alerts* when an `llms.txt` moves, a page 404s, or the Antigravity
   bundle changes. A scheduled canary closes the loop.
3. **Scale the roster to a 4th tool.** There is already an experimental
   `port-claude-code-to-gemini-cli` in `tmp/`. Promoting it exercises whether the
   "hardcoded roster, non-hardcoded concepts" boundary really holds.
4. **Deepen concept coverage (09+).** The registry stops at `08-permissions.md`;
   real portability needs more concepts (env/secrets, output styles, model
   config).
5. **Package for distribution.** Ship as a Claude Code plugin / marketplace entry
   so the experts install in one step instead of being copied.

## Upgrade areas

### 1. Test depth and coverage  *(highest leverage)*
- **Current state.** No `tests/` dir, no CI. Validation is manual black-box Q&A
  (`02-runbook.md` § Tests; `examples/02/README.md` § 6). Regenerating a port
  pair is checked by eyeballing for stray `{{`.
- **Senior-engineer target state.** A `tests/` suite that: (a) asserts every
  generated `port-*/SKILL.md` contains **zero** `{{` placeholders and resolves
  the right slugs; (b) validates every `concept-mapping/ref/0X-*.md` against
  `mapping-file-standard.md` (has the `Porting-in notes` row, a `Sources`
  section, the fixed column order); (c) replays **recorded fixtures** of
  `llms.txt` / a manifest so a doc expert's page-selection logic is testable
  offline without live network. Wired into GitHub Actions.
- **Alternatives.**
  - *Pure structural linting* (grep/markdownlint rules) — cheap, catches
    placeholder + heading drift, but can't test retrieval quality. **Tradeoff:**
    fast and deterministic, but shallow.
  - *Live LLM-judge eval* — ask each doc expert real questions and grade answers
    with a model. **Tradeoff:** tests the thing that matters (answer quality) but
    is flaky, costs tokens, and needs network — bad for CI gating.
  - *Recorded-fixture replay* (recommended middle) — deterministic and offline,
    tests the selection/cap logic, but doesn't catch upstream doc changes (that's
    what area 2 is for).
- **Knowledge prerequisites.** `pytest` fixtures & parametrization; VCR-style
  HTTP record/replay (e.g. `pytest-recording` / `vcrpy`); GitHub Actions matrix
  jobs; how to snapshot-test Markdown structure.
- **Learning path.** pytest docs → `pytest-recording` README → a small "golden
  file" testing tutorial → GitHub Actions `on: push` workflow basics.

### 2. Observability / drift-detection
- **Current state.** Drift is discovered *reactively* — a user notices
  `antigravity-docs` 404s, then runs the index-builder. Nothing watches the three
  upstream indexes. `_(no monitoring in the repo yet)_`
- **Senior-engineer target state.** A scheduled job (GitHub Actions `cron`) that
  weekly: fetches all three indexes, diffs entry counts and slugs against a
  committed snapshot, rebuilds the Antigravity manifest, and opens an issue /
  fails loudly when pages are added/renamed/removed — so "stale" is caught before
  a user hits it.
- **Alternatives.**
  - *Cron canary that only diffs indexes* — light, no answer-quality signal.
  - *Full synthetic-question canary* — runs real questions on a schedule and
    checks answers still cite valid URLs. Richer, but costs tokens and can flake.
  - **Tradeoff:** index-diff is cheap + reliable; question-canary catches subtler
    regressions but is noisier. Start with the diff.
- **Knowledge prerequisites.** GitHub Actions scheduled workflows; the `llms.txt`
  spec; JSON/text diffing; the GitHub Issues API from Actions.
- **Learning path.** Actions `schedule` trigger docs → a "site-change canary"
  blog post → `gh` CLI issue creation from a workflow.

### 3. Scale to a 4th agent (Gemini CLI)
- **Current state.** The roster is **deliberately hardcoded** in
  `port-skill-generator` and `mapping-file-standard.md` § 2 (Claude Code / Codex /
  Antigravity). An experimental `tmp/port-claude-code-to-gemini-cli/` exists but
  isn't promoted, and there is no `gemini-cli-docs` expert.
- **Senior-engineer target state.** Add `gemini-cli-docs` (Layer 1), add a
  Gemini column to every `concept-mapping/ref/0X-*.md` (Layer 2), extend the
  generator roster to make all new port directions generatable (Layer 3). This is
  the true test of the architecture: adding a tool should touch the *generators*
  and *concept files*, never the 12 generated skills.
- **Alternatives.**
  - *Full first-class support* (all layers) — maximal payoff, most work.
  - *Docs-expert only, no porting yet* — quick win, proves the Layer 1 method
    generalizes, defers the N² port surface.
  - **Tradeoff:** doing Layer 1 only is a clean incremental slice; full support
    validates the whole design.
- **Knowledge prerequisites.** Whether Gemini CLI publishes an `llms.txt`-style
  index (repeat the `examples/02` discover-then-verify move); the O(N)
  porting-in-notes trick so the new column doesn't explode the tables.
- **Learning path.** Re-read `examples/02` (discover→verify→encode→test) → apply
  it to Gemini CLI docs → then `concept-mapping-builder` to add the column.

### 4. Concept coverage (Layer 2 depth)
- **Current state.** Concepts `01`–`08` exist (project prompt, settings, skills,
  commands, hooks, MCP, subagents, permissions); `09+` is open
  (`mapping-file-standard.md`).
- **Senior-engineer target state.** Cover the remaining portable concepts:
  environment/secret handling, output styles/personas, model selection, ignore
  files, background/scheduled tasks — each as a `09+` file with full sourcing.
- **Alternatives.** Breadth-first (stub many concepts shallowly) vs depth-first
  (fully source a few). **Tradeoff:** breadth helps the port skills cover more
  ground; depth keeps the "every cell is verified" guarantee intact. Prefer depth
  — a half-sourced concept violates the house rule.
- **Knowledge prerequisites.** Each tool's docs for the new concept (via the
  Layer 1 experts); the mapping-file standard's sourcing + `No equivalent` rules.
- **Learning path.** `mapping-file-standard.md` → an existing rich file like
  `05-hooks.md` as the worked example → `concept-mapping-builder` procedure.

### 5. Packaging / distribution maturity
- **Current state.** Consumed by copying the repo; skills are mirrored to
  `.agents/` **by hand**. No plugin manifest, no versioned release of the bundle.
- **Senior-engineer target state.** A Claude Code **plugin** (or marketplace
  entry) so `claude-code-docs` et al. install in one step; automate the
  `.claude/` → `.agents/` mirror so the two never drift; tag releases.
- **Alternatives.** Plugin packaging vs a plain "clone-and-symlink" install
  script. **Tradeoff:** plugin is the real distribution story but adds a manifest
  to maintain; a script is faster but doesn't scale to other users.
- **Knowledge prerequisites.** Claude Code plugin/marketplace format; semantic
  versioning across a multi-skill bundle; a sync check (CI) between `.claude/` and
  `.agents/`.
- **Learning path.** Claude Code plugins docs (ask `/claude-code-docs`!) → write a
  minimal marketplace manifest → add a CI job that diffs `.claude/` vs `.agents/`.

### 6. Developer experience
- **Current state.** `mise` tasks cover only the Python venv; there's no
  `mise run test` / `lint` / `mirror`.
- **Senior-engineer target state.** `mise` tasks for the smoke checks in
  `02-runbook.md`, a placeholder-lint task, and a mirror task — so contributors
  have one command per job.
- **Alternatives.** `mise` tasks vs a `Makefile` vs `pre-commit` hooks.
  **Tradeoff:** `mise` keeps everything in one already-present file; `pre-commit`
  catches issues earlier but adds a dependency.
- **Knowledge prerequisites.** `mise` task syntax (already used); `pre-commit`
  config basics.
- **Learning path.** `mise.toml` `[tasks.*]` (already in-repo) → add a
  `test`/`lint` task → optionally a `pre-commit` config.
