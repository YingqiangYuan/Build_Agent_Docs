# 05 — Interview Playbook

> **How to use this doc.** These are questions an interviewer would ask about
> this project, each with a **model answer for the interviewer (skill) to grade
> against — never read aloud to the candidate**. Model answers are 3–5 sentences
> and cite where the fact lives. The repo's `examples/03` and `examples/05` are
> the author's own interview script and follow-up playbook; this doc turns them
> into a gradeable question bank plus new pushback rounds derived from
> `03-elevation-roadmap.md`.

---

## Opening — the 90-second pitch (model script)

> "The way I use AI is what I call infinite recursive problem-solving: start from
> the end goal and keep breaking it down until you hit something you can actually
> build, then reassemble upward. Concretely — I needed an always-current expert on
> Claude Code, but the tool changes too fast to memorize. Going through the
> official docs I noticed an easy-to-miss 'Copy page' button; the copied Markdown
> pointed to a site-wide index, `llms.txt`. I didn't trust it — I first had the
> agent confirm `llms.txt` is a real, widely-adopted standard, then used
> `write-agent-skill` to encode a lazy-loading lookup: read the index, fetch 1–3
> pages per question, cap at 9, answer with citations. I tested it on pages it had
> never seen and it grounded every answer. That expert never goes stale because it
> reads live docs each time — and the real value isn't the one expert, it's that I
> now know how to build one for any changing tool. On top of it I built two more
> layers: concept alignment across tools, and automated migration between them."

Grading: a strong pitch leads with the *method* (recursive decomposition), tells
*one concrete firsthand story* (Layer 1), and **stops** — holding Layers 2–3 for
follow-ups (`examples/03` § 5).

## Round 1 — what you have (architecture & mechanism)

- **Q1.1 — "Walk me through what happens, end to end, when someone asks `claude-code-docs` a question."**
  - *Model answer.* It fetches the live `llms.txt` index, matches the question
    against each entry's **description** (not just title), fetches 1–3 relevant
    pages via `WebFetch`, evaluates whether that's enough, and loops — capped at 9
    pages, asking the user before exceeding — then answers with citations. Nothing
    is cached between runs, so a renamed page is picked up automatically next time.
    (`.claude/skills/claude-code-docs/SKILL.md`; `01-knowhow-inventory.md`.)
  - *Follow-ups.* "Why match on description?" "What's the 9-page cap for?" "What if
    the index itself moved?"
  - *Weak answer sounds like.* "It looks up the docs" with no index/cap/citation
    mechanism, or claiming it stores the docs locally.

- **Q1.2 — "You have three doc experts. Why isn't `antigravity-docs` just a copy of the other two?"**
  - *Model answer.* Claude Code and Codex publish a live `llms.txt` with raw `.md`
    page twins, so those skills fetch the index over the network. Antigravity's doc
    site is a client-rendered SPA — fetching a page yields an empty shell and there's
    no `.md` twin — so its index lives on disk as `docs-manifest.json` and content
    sits at separate `/assets/docs/....md` URLs. The answer-time loop is shared; the
    *discovery* mechanism is platform-specific by necessity. (`README.md`;
    `01-knowhow-inventory.md#antigravity-docs`.)
  - *Follow-ups.* "Who builds that manifest?" "How do you know when it's stale?"
  - *Weak answer sounds like.* "They're all the same" — missing the SPA constraint.

- **Q1.3 — "Explain the three layers and how information moves between them."**
  - *Model answer.* Layer 1 = doc experts (read live docs fresh). Layer 2 =
    `concept-mapping` (aligns one concept across all three tools, every cell
    sourced by asking Layer 1). Layer 3 = 12 `port-*` skills (migrate config,
    reading Layer 2's concept list at runtime). Information flows **up exactly once
    per run as a fresh question** — nothing is cached-then-welded — so a doc change
    ripples up automatically. (`01-knowhow-inventory.md`; `examples/04` § 10.)
  - *Follow-ups.* "Where does a fact get written down first?" "What breaks if Layer
    2 caches Layer 1?"
  - *Weak answer sounds like.* Reciting the three layer names with no data-flow.

- **Q1.4 — "Why 12 port skills, and why the doer/checker split?"**
  - *Model answer.* Three tools × 6 pairwise directions × 2 roles = 12. Each
    direction has a doer (creates target config, preserves source) and an
    independent read-only checker that writes a gap report to
    `tmp/review-port-*.md` — so the migrator never grades its own homework.
    (`04-port-skills.md`; `examples/04` § 7.)
  - *Follow-ups.* "Where does the checker write?" "Why not one skill doing both?"
  - *Weak answer sounds like.* Can't justify the split beyond "it's cleaner".

- **Q1.5 — "What's the single design idea that repeats in all three layers?"**
  - *Model answer.* "Don't build the answer — build a mechanism that keeps
    producing it, and pull the layer below fresh." Layer 1: `write-agent-skill`
    then the experts. Layer 2: `concept-mapping-builder` then the concept files.
    Layer 3: `port-skill-generator` then the 12 ports. Generator-then-output, three
    times, nested once more across all three. (`examples/06` § 2–3.)
  - *Follow-ups.* "Where does the recursion stop?" (answer: at the first directly-
    buildable thing toward the end goal.)
  - *Weak answer sounds like.* Describing the layers without naming the shared move.

## Round 2 — what you'd elevate (from `03-elevation-roadmap.md`)

- **Q2.1 — "If you had three more months, what's the first thing you'd add and why?"**
  - *Model answer.* Automated verification — a `tests/` suite asserting every
    generated `port-*/SKILL.md` has zero `{{` placeholders and every
    `concept-mapping/ref/0X-*.md` matches `mapping-file-standard.md`, plus
    recorded-fixture replay of `llms.txt` so page-selection logic is testable
    offline. Today validation is manual Q&A, so this is the biggest credibility
    jump. (`03-elevation-roadmap.md` § 1.)
  - *Follow-ups.* "Why not an LLM-judge eval instead?" (flaky, costs tokens, needs
    network — bad CI gate.)

- **Q2.2 — "Your whole pitch is 'never stale' — but how would you even know when it goes stale?"**
  - *Model answer.* That's the honest gap: drift is currently found reactively when
    a fetch 404s. The upgrade is a scheduled canary that weekly diffs all three
    indexes against a committed snapshot, rebuilds the Antigravity manifest, and
    opens an issue on added/renamed/removed pages. (`03-elevation-roadmap.md` § 2.)
  - *Follow-ups.* "Index-diff or full question-canary?" (start with the cheap
    reliable diff; add the canary later.)

- **Q2.3 — "How would you add a fourth tool, say Gemini CLI?"**
  - *Model answer.* Repeat the `examples/02` move to build `gemini-cli-docs`
    (Layer 1), add a Gemini column to every concept file (Layer 2), and extend the
    generator roster (Layer 3) — and critically, adding a tool should touch the
    *generators and concept files only*, never the 12 generated skills. There's
    already a parked `tmp/port-claude-code-to-gemini-cli/` prototype.
    (`03-elevation-roadmap.md` § 3.)
  - *Follow-ups.* "What if Gemini has no `llms.txt`?" (then you redo discovery from
    scratch — the one genuinely painful case.)

## Round 3 — alternatives considered ("why not X?")

- **Q3.1 — "Why not just copy the docs into the skill and skip the live fetching?"**
  - *Model answer.* Because the copied docs rot the instant upstream renames a slug,
    which is the exact failure the project exists to prevent. Live fetch trades a
    little per-query latency/tokens for permanent freshness, and the 1–3-page cap
    bounds that cost. *Tradeoff matrix:* copy = fast, zero-network, but stale and
    unbounded-context; live-fetch = always-current, cited, bounded — at the cost of
    a network round-trip. (`examples/01`; `04-quiz-bank.md` Q-004.)

- **Q3.2 — "Why not one big migration guide per direction instead of destination-keyed porting notes?"**
  - *Model answer.* Per-direction guides grow O(N²) as tools are added; keying the
    `Porting-in notes` row by *destination* makes it O(N) — one note per tool, since
    migration pain lives on the receiving end. *Tradeoff:* per-direction is slightly
    more explicit for a single move, but doesn't scale and rewrites on every new
    direction; destination-keyed never rewrites. (`examples/04` § 5;
    `mapping-file-standard.md`.)

- **Q3.3 — "Why generate the 12 port skills instead of hand-writing them, or writing one parametric skill?"**
  - *Model answer.* Hand-writing 12 near-identical files invites drift; a single
    generator + two templates is one source of truth. A single runtime-parametric
    skill was possible but generation keeps each skill independently discoverable
    and inspectable while still sharing behavior via templates. *Tradeoff:*
    generation adds a build step; hand-writing adds drift risk; one parametric skill
    hides the surface. (`examples/04` § 8; `port-skill-generator/SKILL.md`.)

## Round 4 — problems hit / debugging

- **Q4.1 — "Antigravity docs suddenly return empty content on fetch. How do you debug it?"**
  - *Model answer.* Empty content is the SPA symptom — the page URL only returns a
    shell. You don't fetch page URLs for Antigravity; you read the manifest and
    fetch each page's `content_url`. If those 404, the manifest is stale → rebuild
    with `/antigravity-docs-index-builder --force`. If the *builder* fails with
    "could not find `main-<hash>.js`" the app shell changed (patch
    `find_bundle_name`); "DOCS_STRUCTURE not found" means the record shape changed
    (patch `parse_structure`). (`02-runbook.md` § Common failures.)

- **Q4.2 — "A generated port skill still has `{{PLACEHOLDER}}` in it. What went wrong and how do you fix it, correctly?"**
  - *Model answer.* A substitution was missed during generation. The *wrong* fix is
    editing the generated file — that reintroduces the drift generation exists to
    prevent. The right fix is re-running `/port-skill-generator <src> to <tgt>`,
    and adding the invariant to the test suite (`grep -R "{{"` must be empty).
    (`02-runbook.md`; `03-elevation-roadmap.md` § 1.)

## Round 5 — production pushbacks (senior-level pressure)

- **Q5.1 — "One of these tools rips out its `llms.txt` entirely. What happens to your system?"**
  - *Model answer.* Layer 1 for that tool breaks at discovery — you'd redo the
    discover→verify step from scratch (e.g. the manifest approach Antigravity
    already forced). Layer 2 takes a localized hit: re-source that tool's column.
    Layer 3 is nearly untouched because it never hardcodes concepts. It's the one
    genuinely painful scenario, but low-probability and handled with the same
    method. (`examples/05` § 3.)

- **Q5.2 — "You're leaning hard on an agent to do the work. If I claim the AI did everything and you did nothing, defend yourself."**
  - *Model answer.* The AI executed — crawling, writing skills, testing — but the
    decisions were mine: noticing the Copy-page button mattered, refusing to trust
    `llms.txt` unverified, choosing 'build a mechanism not the answer' three
    separate times, and keying porting notes by destination to dodge the N²
    explosion. Those are architecture calls the AI didn't originate. Execution is
    commoditized; the decomposition is the skill. (`examples/05` § 5.)

- **Q5.3 — "This is all Markdown with no tests and no CI. Why should I trust it in production?"**
  - *Model answer.* Fair — today it's validated by manual black-box Q&A, and I'd
    call that the top gap, not paper over it. The structure is testable, though:
    placeholder-lint, standard-conformance checks, and fixture replay give
    deterministic CI without network, and a scheduled index-diff canary catches
    upstream drift. That's a concrete, honest hardening plan rather than a claim
    that it's already bulletproof. (`03-elevation-roadmap.md` § 1–2.)

- **Q5.4 — "Scale this to 50 tools. Where does the design strain first?"**
  - *Model answer.* The concept tables gain a column per tool (linear, fine), and
    porting-in notes stay O(N) per concept. The real strain is Layer 1 breadth —
    50 discovery mechanisms to build and monitor — and the port surface if you want
    all pairwise directions (that's genuinely O(N²) *skills*, though each is
    generated). I'd prioritize the docs experts + concept columns for all 50, and
    generate port pairs on demand rather than eagerly. (`03-elevation-roadmap.md`
    § 3, 5.)
