# 04 — Quiz Bank

## How these questions are designed

These are **discussion prompts, not fill-in-the-blank recall**. The point of
each item is to make you (a) *find the answer in the repo* — name a file path or
doc anchor — and (b) *articulate the underlying reason* — 知其然知其所以然.

1. Every question is open-ended. A good answer is **3–5 sentences** that names
   file paths **and** explains the principle.
2. If a question can be answered in one sentence, the question was too narrow.
3. Scoring standard: an answer must engage **where to look + what + why**. A
   factually correct one-liner that names no file and no rationale is ⚠️ partial,
   not ✅.

### What good vs bad questions look like
- ❌ Bad: "Where does `claude-code-docs` fetch its index from?" → recites one URL.
- ✅ Good: "Walk through why all three doc experts re-read their index every run
  instead of caching it — what would break if they cached, and where is that rule
  written down?"
- ❌ Bad: "How many port skills are there?" → a number.
- ✅ Good: "Why are there exactly 12 port skills, and why is each direction split
  into a doer and a checker rather than one skill doing both?"

## Setup & runbook

- **Q-001** [tag: runbook, difficulty: easy]
  - **Q:** A teammate clones this repo and asks "what do I install to run it?" Where do you point them, and what would you tell them about how little the Python setup actually matters here?
  - **A:** Point them at `mise.toml` — it declares the runtime (`python 3.12`, `uv`) and the three tasks (`venv-create`, `inst`, `venv-remove`). But the honest answer (see `02-runbook.md` § Scope note) is that the Python env is *scaffolding*: nothing in the skills exercises `httpx2`, and you can use every skill with no venv at all. The thing that actually "runs" is a skill invoked inside Claude Code, e.g. `/claude-code-docs <question>`. So the toolchain question is almost a trick — the real entry point is `.claude/skills/`, not `.venv/`.
  - **Source:** `mise.toml`, `docs/learn-this-project/02-runbook.md`

- **Q-002** [tag: runbook, difficulty: medium]
  - **Q:** There's no `tests/` directory. If someone asks "how do you know the skills actually work?", how do you answer, and what would a first real test assert?
  - **A:** Today validation is **manual black-box Q&A** — you ask a doc expert about pages it has never seen and confirm it cites a real source (`examples/02/README.md` § 6; `02-runbook.md` § Tests). The cheapest real test asserts structural invariants: every generated `port-*/SKILL.md` contains zero `{{` placeholders, and every `coding-agent-concept-mapping/ref/0X-*.md` has a `Porting-in notes` row and a `Sources` section. This matters because the payload is generated Markdown, so drift shows up as broken structure, not a stack trace. Recorded-fixture replay of `llms.txt` (see `03-elevation-roadmap.md` § 1) is the next rung up.
  - **Source:** `docs/learn-this-project/02-runbook.md`, `docs/learn-this-project/03-elevation-roadmap.md`

- **Q-003** [tag: runbook, difficulty: medium]
  - **Q:** A user reports `/antigravity-docs` is returning 404s on a page it used to find. Where do you look, what's the likely cause, and why does this failure mode exist for Antigravity but not for Claude Code?
  - **A:** The manifest at `.claude/skills/antigravity-docs/references/docs-manifest.json` is stale — its `content_url`s point at pages that moved. Fix: `/antigravity-docs-index-builder --force`. This can't happen the same way for `claude-code-docs` because that skill re-fetches its `llms.txt` index *live every run*, whereas Antigravity's index is a **local file** (its doc site is a client-rendered SPA with no fetchable index). So Antigravity trades live-freshness for a build step, and the cost of that trade is exactly this stale-manifest failure. See `01-knowhow-inventory.md#antigravity-docs`.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `.claude/skills/antigravity-docs/references/docs-manifest.json`

## Layer 1 — documentation experts

- **Q-004** [tag: knowhow, difficulty: medium]
  - **Q:** All three doc experts re-read their index on every invocation instead of caching page content. Walk through why, and what specifically would break if they cached.
  - **A:** The value proposition is "never stale" — Claude Code / Codex / Antigravity rename slugs and restructure docs frequently (`README.md`; `examples/01`). If a skill cached page content, its answers would silently rot the moment upstream changed, which is the exact failure the project exists to avoid. Re-reading the index each run means a renamed page is picked up automatically on the next question. The `SKILL.md` "rules" encode this as "never skip the index read; never invent doc URLs." The cost is a little latency and tokens per query, which the 1–3-page batching keeps bounded.
  - **Source:** `.claude/skills/claude-code-docs/SKILL.md`, `docs/learn-this-project/01-knowhow-inventory.md`

- **Q-005** [tag: knowhow, difficulty: medium]
  - **Q:** Why do the doc experts fetch only 1–3 pages per batch and cap at 9 pages total, then *ask* before continuing — rather than just fetching everything relevant up front?
  - **A:** A docs site has hundreds of pages; dumping them into context is wasteful and slow, and most questions need only a page or two (`examples/02` § 6). Fetching 1–3, re-evaluating, and looping means the agent reads the *minimum* to answer, and the 9-page cap is a circuit-breaker against runaway fetching on a vague question. Stopping to ask the user keeps a human in the loop when the question is genuinely too broad, instead of burning tokens guessing. It's lazy-loading + agentic search, written as an explicit procedure in each `SKILL.md`.
  - **Source:** `.claude/skills/claude-code-docs/SKILL.md`, `docs/learn-this-project/02-docs-skills.md`

- **Q-006** [tag: knowhow, difficulty: hard]
  - **Q:** `claude-code-docs` and `codex-docs` are nearly identical, but `antigravity-docs` is structurally different. Explain the difference and why one template couldn't cover all three.
  - **A:** Claude Code and Codex both publish a live `llms.txt` whose links resolve to raw `.md` twins, so those skills lazy-load the index over the network and fetch pages directly. Antigravity's doc site is a **client-rendered SPA**: fetching a page URL returns an empty shell and there's no `.md` twin, so its index can't be fetched live — it lives on disk as `docs-manifest.json`, and content sits at separate `/assets/docs/....md` URLs (`README.md`; `01-knowhow-inventory.md#antigravity-docs`). This is why `examples/02` insists each expert's *discovery mechanism* be designed on its own terms — the answer-time loop is shared, but how you get the index is platform-specific.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `README.md`

- **Q-007** [tag: knowhow, difficulty: medium]
  - **Q:** Matching a question against the index entry's *description* rather than just its *title* is a deliberate choice. Why does it matter?
  - **A:** Titles are terse and often don't contain the words a user would ask with; the `llms.txt` description is a one-line summary that carries the real keywords (`01-knowhow-inventory.md#claude-code-docs`). Matching on description means a question phrased differently from the page title still routes correctly, improving retrieval without fetching the page first. It's a cheap relevance signal that keeps the 1–3-page budget spent on the right pages. The rule is written into each doc expert's procedure.
  - **Source:** `.claude/skills/claude-code-docs/SKILL.md`, `.claude/skills/codex-docs/SKILL.md`

- **Q-008** [tag: mech, difficulty: hard]
  - **Q:** `antigravity-docs-index-builder` uses `curl`/`urllib` for the JS bundle instead of `WebFetch`. Walk through why that specific choice is forced.
  - **A:** The Antigravity doc map lives inside the web app's JavaScript bundle as a `DOCS_STRUCTURE` object. `WebFetch` markdown-converts pages and **strips `<script>` tags**, so it literally cannot see that object; you need the raw bytes, which `curl`/`urllib` deliver (`01-knowhow-inventory.md#antigravity-docs-index-builder`). The script then joins `DOCS_STRUCTURE` against `llms.txt` on slug to attach titles/descriptions and writes `docs-manifest.json`. It's a good example of picking the tool to fit the data shape rather than defaulting to the convenient one.
  - **Source:** `.claude/skills/antigravity-docs-index-builder/scripts/build_manifest.py`, `docs/learn-this-project/01-knowhow-inventory.md`

- **Q-009** [tag: knowhow, difficulty: medium]
  - **Q:** Why is index-*building* split into its own skill (`antigravity-docs-index-builder`) rather than folded into `antigravity-docs`?
  - **A:** Separating the generator from the consumer means the doc map can be refreshed (re-run the builder when Antigravity ships new pages) without changing the lookup skill at all (`docs/02-docs-skills.md` § 1). The lookup skill stays simple and read-mostly; the builder holds all the fragile bundle-parsing logic. This is the same generator-then-output split the whole repo repeats — and it localizes the "docs changed" blast radius to one rebuild.
  - **Source:** `docs/learn-this-project/02-docs-skills.md`, `.claude/skills/antigravity-docs-index-builder/SKILL.md`

- **Q-010** [tag: knowhow, difficulty: hard]
  - **Q:** The `examples/02` story spends a whole section on *verifying* that `llms.txt` is a real standard before building on it. Why was that step non-negotiable?
  - **A:** A mechanism that looks perfect on one page might be a coincidence or a redesign artifact; building on it untested means standing on sand (`examples/02` § 5). So the discovery was handed to Claude to search the web and confirm `llms.txt` is a widely-adopted, official convention for AI agents — only then was it worth encoding. This "discover → **verify** → encode → test" skeleton is the reusable four-move pattern (`examples/03`), and skipping verify is what separates methodical work from getting lucky.
  - **Source:** `examples/02-building-the-first-expert/README.md`, `examples/03-the-interview-story/README.md`

- **Q-011** [tag: knowhow, difficulty: medium]
  - **Q:** `write-agent-skill`'s `SKILL.md` is almost empty, with the real content in `references/extend-claude-with-skills.md`. Why structure it that way, and how does it connect to Layer 1's story?
  - **A:** Keeping `SKILL.md` thin and pushing the 300-line guide into a `references/` file is the same lazy-load philosophy the doc experts use — load the heavy content only when the skill is actually engaged (`01-knowhow-inventory.md#write-agent-skill`). More importantly, `write-agent-skill` is the *generator that precedes Layer 1's output*: the three doc experts were written using it. Encoding the method first, then producing experts with it, is the pattern that recurs in Layers 2 and 3.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `examples/02-building-the-first-expert/README.md`

## Layer 2 — concept alignment

- **Q-012** [tag: knowhow, difficulty: medium]
  - **Q:** Once you have three doc experts, what problem remains that `coding-agent-concept-mapping` exists to solve? Frame it as a scenario.
  - **A:** Each expert knows only its own tool; none knows whether its answer lines up with the other two (`examples/04` § 3). If you ask "where do skills live?" three separate times, you get three scattered answers and must stitch them yourself — and the stitched conclusion has nowhere to live, so the next person redoes it. `coding-agent-concept-mapping` records the alignment once, in `ref/0X-*.md`, so the depth you built on one tool transfers by precise analogy. That's the "learning accelerator" motivation in `examples/04` § 2.
  - **Source:** `examples/04-building-layers-two-and-three/README.md`, `.claude/skills/coding-agent-concept-mapping/SKILL.md`

- **Q-013** [tag: knowhow, difficulty: hard]
  - **Q:** The `Porting-in notes` row is organized *by destination tool*, not *by migration direction*. Walk through why, and what it prevents.
  - **A:** With three tools there are six pairwise directions; if each dimension spelled out "moving from X to Y", the tables would grow quadratically as tools are added (`examples/04` § 5). Instead each concept table has **one note per tool** answering "what bites when config arrives *at this tool*" — because migration pain lives on the receiving end. Three tools → three cells, and adding a direction never rewrites the row. This O(N)-instead-of-O(N²) trick is defined in `coding-agent-concept-mapping-builder/ref/mapping-file-standard.md` and is the same "reach for a smarter structure" instinct Layer 3 reuses.
  - **Source:** `examples/04-building-layers-two-and-three/README.md`, `.claude/skills/coding-agent-concept-mapping-builder/ref/mapping-file-standard.md`

- **Q-014** [tag: knowhow, difficulty: medium]
  - **Q:** Why is Claude Code always the first/seed column in every concept file, and what would go wrong without a fixed seed?
  - **A:** The standard makes Claude Code the seed that frames each concept's vocabulary and decomposition; the other two columns describe how they realize the *same* idea or note `No equivalent` (`docs/03-coding-agent-concept-mapping.md`; `mapping-file-standard.md`). Without a fixed anchor, different concept files would name and slice the same idea differently, and the tables would stop being comparable. A consistent seed is what makes the mapping a genuine alignment rather than three parallel glossaries.
  - **Source:** `docs/learn-this-project/03-coding-agent-concept-mapping.md`, `.claude/skills/coding-agent-concept-mapping-builder/ref/mapping-file-standard.md`

- **Q-015** [tag: knowhow, difficulty: medium]
  - **Q:** `coding-agent-concept-mapping` is read-only and `coding-agent-concept-mapping-builder` does all writing. Why split them, and what's the maintenance order the builder must follow?
  - **A:** The query-time skill stays read-only so answering can never accidentally invent or mutate facts; all authoring — with its doc-sourcing discipline — lives in the builder (`docs/03-coding-agent-concept-mapping.md`). The builder's fixed order is **detail file first, index second**: update `ref/0X-concept.md`, then regenerate `ref/00-context-index.md`, because the index is just navigation and must never be where a new fact first appears (`examples/04` § 6). Reversing that order would let the index and the detail files disagree.
  - **Source:** `.claude/skills/coding-agent-concept-mapping-builder/SKILL.md`, `docs/learn-this-project/03-coding-agent-concept-mapping.md`

- **Q-016** [tag: convention, difficulty: medium]
  - **Q:** The mapping standard forbids blank cells and requires a `Sources` section. What principle do both rules enforce?
  - **A:** Both enforce "never from memory, always grounded" (`mapping-file-standard.md`). A blank cell is ambiguous — did the author not check, or is there genuinely no equivalent? — so the rule requires `No equivalent` + context instead, making absence explicit. The `Sources` section records exactly which doc page each non-obvious claim came from (URLs in raw `.md` form) so any cell can be re-verified later. Together they make the knowledge base auditable rather than trust-me.
  - **Source:** `.claude/skills/coding-agent-concept-mapping-builder/ref/mapping-file-standard.md`, `.claude/skills/coding-agent-concept-mapping/ref/03-skills.md`

- **Q-017** [tag: mech, difficulty: medium]
  - **Q:** Trace how a single cell in `03-skills.md` gets its value. Who produces it and against what source?
  - **A:** `coding-agent-concept-mapping-builder` produces it: for the skills concept it asks `claude-code-docs` for the Claude Code column, `codex-docs` for the Codex column, and `antigravity-docs` for the Antigravity column, then fills the cell and records the doc page in `Sources` (`examples/04` § 4). So the cell's value flows *up* from Layer 1, verified fresh, never written from training memory. This is why a tool changing its docs only requires re-running the builder for that one concept.
  - **Source:** `.claude/skills/coding-agent-concept-mapping/ref/03-skills.md`, `examples/04-building-layers-two-and-three/README.md`

## Layer 3 — migration

- **Q-018** [tag: knowhow, difficulty: medium]
  - **Q:** Why are there exactly 12 port skills, and why is each direction split into a doer and a checker?
  - **A:** Three tools convert pairwise in 6 directions, and each direction needs two roles — an executor and an auditor — giving 12 (`docs/04-port-skills.md`; `examples/04` § 7). The split exists so the skill that performed a migration never grades its own work: the checker is read-only and independent, scanning both sides and writing a gap report. Letting the doer self-assess would hide exactly the mistakes you most need to catch.
  - **Source:** `docs/learn-this-project/04-port-skills.md`, `examples/04-building-layers-two-and-three/README.md`

- **Q-019** [tag: knowhow, difficulty: hard]
  - **Q:** The 12 port skills are generated, not hand-written. Explain the failure this prevents and how the generator is structured to prevent it.
  - **A:** Twelve near-identical files differing only by source/target names drift the instant you fix one and forget another (`examples/04` § 8). So `port-coding-agent-skill-generator` holds two templates (`ref/port-skill-template.md`, `ref/checker-skill-template.md`) with `{{SOURCE_NAME}}`/`{{TARGET_NAME}}`-style placeholders; running `/port-coding-agent-skill-generator cc to cdx` resolves the names and stamps out both `SKILL.md`s. To change shared behavior you edit a template and regenerate — you never hand-edit a generated file. Same generator-before-output pattern as `write-agent-skill` and `coding-agent-concept-mapping-builder`.
  - **Source:** `.claude/skills/port-coding-agent-skill-generator/SKILL.md`, `examples/04-building-layers-two-and-three/README.md`

- **Q-020** [tag: knowhow, difficulty: hard]
  - **Q:** The generator hardcodes the *agent roster* but deliberately does *not* hardcode the *concept list*. Walk through why the two lists are treated differently.
  - **A:** The set of agents is small and stable — adding a fourth tool is a rare event — so baking the name/slug/docs-skill lookup into the generator is fine (`docs/04-port-skills.md`). But the set of portable concepts keeps growing, so the templates never carry a concept list; every generated port/checker skill reads it fresh from `coding-agent-concept-mapping/ref/00-context-index.md` at runtime (`examples/04` § 9). The payoff: adding a new concept updates Layer 2 once and all 12 skills follow automatically, with no file touched.
  - **Source:** `docs/learn-this-project/04-port-skills.md`, `examples/04-building-layers-two-and-three/README.md`

- **Q-021** [tag: mech, difficulty: medium]
  - **Q:** Where does a checker skill write its output, what's in it, and why is that the *only* thing it writes?
  - **A:** It writes `tmp/review-port-<source>-to-<target>.md` inside the target project — a fixed structure with a Summary (concepts present / fully ported / gaps / skipped) and a `Gaps` section per concept (present-on-source, state-on-target, what's-missing, suggested-change, priority) (`01-knowhow-inventory.md`; `04-port-skills.md`). It writes nothing else because it's an *auditor*: touching project config would make it a second doer and destroy the independent-review guarantee. The report is advice, not applied changes.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `docs/learn-this-project/04-port-skills.md`

- **Q-022** [tag: knowhow, difficulty: medium]
  - **Q:** A port skill migrates config but "preserves the source". Why keep the source instead of moving it, and what does that imply about the migration's reversibility?
  - **A:** The doer creates/edits the target-tool files *alongside* the existing source files rather than replacing them (`01-knowhow-inventory.md`; port template). Keeping the source means the migration is additive and non-destructive — if the port is wrong, nothing was lost, and you can re-run or audit safely. This is the same "do no harm by default" instinct as the read-only checker: the enterprise value is *portability*, which you undermine if migrating means burning the origin.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `.claude/skills/port-coding-agent-skill-generator/ref/port-skill-template.md`

## The mental model & cross-cutting design

- **Q-023** [tag: knowhow, difficulty: hard]
  - **Q:** The repo repeats one design move in all three layers. State it precisely and give the concrete instance in each layer.
  - **A:** The move is **"don't build the final answer directly — build a mechanism that keeps producing it, and always pull the layer below fresh"** (`examples/06` § 2). Layer 1: build `write-agent-skill` (the method), then produce `claude-code-docs`. Layer 2: build `coding-agent-concept-mapping-builder` (+ standard), then produce `03-skills.md` et al. Layer 3: build `port-coding-agent-skill-generator` (+ two templates), then stamp the 12 ports (`examples/06` § 3). Each is generator-then-output; the pattern even nests once more across all three layers combined.
  - **Source:** `examples/06-the-mental-model-recursive-decomposition/README.md`, `examples/04-building-layers-two-and-three/README.md`

- **Q-024** [tag: knowhow, difficulty: hard]
  - **Q:** "Infinite recursive decomposition" is the repo's headline idea. Explain how "start from the end goal" decides where the recursion *stops*.
  - **A:** You fix the real end goal, ask whether you can build it directly; if not, step back to "can I build a mechanism that keeps producing it?", and keep stepping back until you reach something you can build by hand — that point is your foundation, and you reassemble upward from there (`examples/06` § 2). Starting from the end goal is what decides where to stop stepping back: you stop at the first thing that's directly buildable toward *that* goal. Recursion just says each step back is a smaller copy of the same question. In this repo the foundation is `write-agent-skill`; the top goal is lock-in-free cross-agent migration.
  - **Source:** `examples/06-the-mental-model-recursive-decomposition/README.md`

- **Q-025** [tag: knowhow, difficulty: medium]
  - **Q:** "Information flows upward exactly once per run, always as a fresh question." Unpack what that guarantees when a tool changes its docs.
  - **A:** Layer 3 reads Layer 2's concept list at runtime; Layer 2's cells were each verified by asking Layer 1; Layer 1 re-reads the live index each run (`examples/04` § 10; `01-knowhow-inventory.md` architecture). So a doc change is absorbed at Layer 1 automatically, a behavior change means re-running the builder for *one* concept file, and Layer 3 is almost never touched because it never hardcodes concepts. Nothing is cached-then-welded, so a change ripples up instead of forcing a manual sync of twelve places.
  - **Source:** `examples/04-building-layers-two-and-three/README.md`, `docs/learn-this-project/01-knowhow-inventory.md`

- **Q-026** [tag: knowhow, difficulty: medium]
  - **Q:** Each layer "races against" a different specific risk. Name the three races and how the design wins each.
  - **A:** Layer 1 races **doc staleness** — won by re-reading the index fresh every run (`examples/06` § "same pattern"). Layer 2 races **combinatorial explosion** — won by destination-keyed porting-in notes (O(N) not O(N²)). Layer 3 races **manual-maintenance drift** across 12 files — won by generating them from two templates and reading the concept list at runtime. Different enemies, but the same counter-move each time: build a mechanism, don't hand-maintain the answer.
  - **Source:** `examples/06-the-mental-model-recursive-decomposition/README.md`, `examples/04-building-layers-two-and-three/README.md`

- **Q-027** [tag: convention, difficulty: medium]
  - **Q:** Across the repo, skills request narrow `allowed-tools` (e.g. `coding-agent-concept-mapping` gets only `Read`; the checker never gets project-config write). What discipline is this, and why does it matter for a migration tool specifically?
  - **A:** It's deny-by-default least-privilege: a skill gets only the tools its job needs (`01-knowhow-inventory.md` § Conventions). For the checker it's load-bearing — granting it only read + a single report write is what *structurally* prevents it from modifying the project it's auditing, so the doer/checker independence isn't just convention, it's enforced by the tool grant. A read-only query skill that could write could silently corrupt the knowledge base.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `.claude/skills/port-coding-agent-skill-generator/ref/checker-skill-template.md`

- **Q-028** [tag: knowhow, difficulty: medium]
  - **Q:** Why are the three doc experts also mirrored under `.agents/skills/`, and what does that have to do with the concept map?
  - **A:** `.agents/skills/` is the **tool-neutral** discovery path that Codex and Antigravity read, whereas `.claude/skills/` is Claude Code's path (`01-knowhow-inventory.md` § Supporting; `coding-agent-concept-mapping/ref/03-skills.md`). Mirroring the doc experts there lets other agents load them too, making the experts portable rather than Claude-only. It's a small live demonstration of the very portability the concept map documents and the port skills automate.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `.claude/skills/coding-agent-concept-mapping/ref/03-skills.md`

- **Q-029** [tag: deps, difficulty: medium]
  - **Q:** The project depends on `WebFetch` for the doc experts but drops to `curl`/`urllib` for exactly one job. What does that inconsistency teach about choosing dependencies?
  - **A:** `WebFetch` is chosen everywhere because official docs expose raw `.md`, so no HTML parsing is needed — the tool fits the data (`01-knowhow-inventory.md` § External deps). But it markdown-converts and strips `<script>`, so for the one job that needs a JS bundle's `DOCS_STRUCTURE`, it's the *wrong* tool and raw-byte `curl`/`urllib` is used instead. The lesson: pick the dependency by the shape of the data you're touching, and don't force the convenient default where it structurally can't work.
  - **Source:** `docs/learn-this-project/01-knowhow-inventory.md`, `.claude/skills/antigravity-docs-index-builder/scripts/build_manifest.py`

- **Q-030** [tag: knowhow, difficulty: hard]
  - **Q:** `examples/03` insists the interview pitch stop at Layer 1 and *hold back* Layers 2 and 3. Why is deliberately telling less the stronger move?
  - **A:** Dumping the whole three-layer architecture up front reads like reciting a memorized script and dilutes one concrete, firsthand experience into a vague overview (`examples/03` § 5). Stopping at the fully-owned Layer-1 story — discover the Copy-page button, find `llms.txt`, verify it, encode it, test it — means every step survives probing because you actually did it. Letting the interviewer *ask* for Layers 2–3 proves you can decompose to whatever depth they push, which is itself the AI-native thinking being tested. Restraint invites the follow-up that `examples/05` is built to field.
  - **Source:** `examples/03-the-interview-story/README.md`, `examples/05-answering-follow-up-questions/README.md`

- **Q-031** [tag: knowhow, difficulty: medium]
  - **Q:** `examples/05` answers "did you actually do anything, or did the AI do it all?" by listing four decisions. Why are those four the load-bearing part of the story, not the crawling/coding the AI did?
  - **A:** The AI did the execution — crawling docs, writing skills, running tests — but the *decisions* were human: noticing the Copy-page button mattered, refusing to trust `llms.txt` without verifying, choosing "build a mechanism not the answer" three separate times, and keying porting notes by destination to dodge the N² explosion (`examples/05` § 5). Those are architectural judgment calls the AI didn't originate, and they're what "solving via infinite recursion" actually means in practice. Execution is commoditized; the decomposition is the skill being demonstrated.
  - **Source:** `examples/05-answering-follow-up-questions/README.md`

- **Q-032** [tag: knowhow, difficulty: hard]
  - **Q:** `examples/05` claims this method transfers to problems unrelated to coding agents (paper-tracking, a team Scrum Master). Pick one and walk through how the *same* four-move skeleton maps onto it.
  - **A:** Take daily paper/news tracking (`examples/05` § 6): **discover** whether the source publishes a machine-readable index like `llms.txt`; **verify** it's a stable, sanctioned mechanism, not improvised; **encode** the discovery as a Skill that fetches the latest entries fresh each run instead of you checking manually; **test** it against topics it's never seen to confirm accuracy. It's the exact skeleton that built `claude-code-docs`, pointed at an unrelated domain — which is the whole point of `examples/01`'s claim that a coding agent is a general-purpose productivity engine, and of `examples/06`'s argument that the mental model isn't keyed to Claude Code at all.
  - **Source:** `examples/05-answering-follow-up-questions/README.md`, `examples/06-the-mental-model-recursive-decomposition/README.md`
