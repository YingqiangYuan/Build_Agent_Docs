# 01 — Knowhow Inventory

> **Scope note.** This is an *Agent-Skills* project, not a Python project. The
> `pyproject.toml` / `.venv/` / `httpx2` dependency is incidental scaffolding —
> the actual "code" is a set of **Markdown `SKILL.md` files** under
> `.claude/skills/`, plus their `ref/`, `references/`, and `scripts/` support
> files. Read every component below as "a skill (a folder with a `SKILL.md`)",
> not "a module". The narrative that ties it all together lives in `examples/`
> (a six-part interview story) and in the four English `docs/0X-*.md` overviews.

---

## Project at a glance

`learn_build_agent_docs_skill` teaches a coding agent how to **build its own
documentation experts** for fast-moving AI coding tools, instead of relying on
stale training data. The payload is a **three-layer stack**:

1. **Layer 1 — documentation experts.** One skill per tool (`claude-code-docs`,
   `codex-docs`, `antigravity-docs`) that discovers the tool's official docs
   index and lazy-fetches only the pages a question needs.
2. **Layer 2 — concept alignment.** `concept-mapping` — a knowledge base that
   lines up the *same* configuration concept (skills, hooks, MCP, permissions…)
   across all three tools, so depth learned on one tool transfers precisely to
   the others.
3. **Layer 3 — migration.** 12 `port-*` skills (6 directions × doer+checker)
   that actually carry a project's config from one tool to another, dissolving
   vendor lock-in.

The repeated design move — visible in all three layers — is **"don't build the
answer, build the mechanism that keeps producing the answer, and always pull the
layer below fresh."** Each layer has a *generator* that comes first and a
*concrete output* that comes second: `write-agent-skill`→the 3 doc experts,
`concept-mapping-builder`→the concept files, `port-skill-generator`→the 12 ports.

**Who uses it:** developers juggling multiple coding agents; the repo's author
as an interview portfolio piece (the `examples/` folder is a ready-to-tell
interview story); Agent-Skill authors wanting a reference implementation.

## Architecture overview

```
                    ┌─────────────────────────────────────────────┐
   End goal:        │ enterprise-grade cross-agent migration,      │
   (work backward)  │ lock-in free                                 │
                    └───────────────────────▲─────────────────────┘
                                             │ delivers
  LAYER 3  port-skill-generator ──generates──> 12 port-* skills (doer + checker)
   (do)     (2 templates)                        │ reads concept list fresh
                                                  ▼
  LAYER 2  concept-mapping-builder ──writes──> concept-mapping/ref/*.md (00 index + 01–08)
   (align)  (mapping-file-standard)              │ every cell verified against ↓
                                                  ▼
  LAYER 1  write-agent-skill ──method──> claude-code-docs / codex-docs / antigravity-docs
   (read)                                         │ fetch official docs fresh, never from memory
                                                  ▼
                              official docs sites (llms.txt / JS bundle manifest)
```

Information flows **upward exactly once per run, always as a fresh question**:
Layer 3 asks Layer 2 for the current concept list at runtime; Layer 2's cells
were each verified by asking Layer 1; Layer 1 re-reads the live docs index every
time. That is why a doc change or a new concept ripples up the whole chain
automatically instead of needing 12 files hand-synced.

## Component inventory

### Layer 1 — Documentation experts

#### `claude-code-docs`
- **What.** Answers Claude Code / Agent SDK / hooks / MCP / skills / settings
  questions by fetching the live official docs on demand.
- **Why.** Claude Code changes fast; a skill that re-reads `llms.txt` every run
  never goes stale, unlike facts baked into a prompt or training data.
- **Key files.** `.claude/skills/claude-code-docs/SKILL.md`, `CHANGELOG.md`, `VERSION`, `README-cn.md`.
- **Depends on.** `WebFetch` tool; the site index `https://code.claude.com/docs/llms.txt`.
- **Gotchas.** Procedure is a *loop with a cap*: match the question against each
  index entry's **description** (not just its title), fetch **1–3 pages per
  batch**, re-evaluate, and **stop at 9 pages**, asking the user before going
  further. Never invent doc URLs; never skip the index read (slugs get renamed).

#### `codex-docs`
- **What.** Same shape as `claude-code-docs`, for OpenAI Codex (CLI, IDE, app,
  cloud, sandboxing, MCP, config, enterprise).
- **Why.** Identical rationale; Codex also publishes a machine-readable
  `llms.txt`, so the same lazy-load-and-cap mechanism transfers directly.
- **Key files.** `.claude/skills/codex-docs/SKILL.md` (+ `CHANGELOG.md`, `VERSION`, `README-cn.md`).
- **Depends on.** `WebFetch`; index `https://developers.openai.com/codex/llms.txt`.
- **Gotchas.** Scoped to `developers.openai.com/codex/*` only — the general
  OpenAI API is deliberately out of scope. Same 1–3-per-batch / 9-page cap.

#### `antigravity-docs`
- **What.** Doc expert for Google Antigravity — but discovers pages via a
  **local manifest** instead of a live `llms.txt`.
- **Why (the interesting one).** Antigravity's doc pages are a **client-rendered
  SPA**: fetching a page URL returns an empty shell, and there is no `.md` twin.
  So the index can't be fetched live like the other two. Instead the manifest
  lives on disk and each page's real content sits at a separate
  `/assets/docs/....md` URL.
- **Key files.** `.claude/skills/antigravity-docs/SKILL.md`,
  `.claude/skills/antigravity-docs/references/docs-manifest.json`
  (`_meta` + `pages[{section, slug, title, description, content_url}]`).
- **Depends on.** `Read` (for the manifest) + `WebFetch` (for `content_url`s);
  the manifest is produced by `antigravity-docs-index-builder`.
- **Gotchas.** A 404 on a `content_url` means the manifest is **stale** → run
  `/antigravity-docs-index-builder`. Cite the human page
  `https://antigravity.google/docs/<slug>` even though you fetched the `.md` twin.

#### `antigravity-docs-index-builder`
- **What.** Regenerates `antigravity-docs`'s `docs-manifest.json` from
  Antigravity's live web-app JS bundle.
- **Why.** Splitting *index-building* from *answering* keeps the doc map
  refreshable (re-run the builder) without touching the lookup skill — the same
  generator-then-output split seen everywhere in this repo.
- **Key files.** `.claude/skills/antigravity-docs-index-builder/SKILL.md`,
  `scripts/build_manifest.py`.
- **Depends on.** `Bash`, `Read`, `Write`; `curl`/`urllib` (raw bytes — `WebFetch`
  strips `<script>` tags so it can't see `DOCS_STRUCTURE`).
- **Gotchas.** Never hand-edit the manifest. The script short-circuits when the
  bundle hash is unchanged; pass `--force` to override, set
  `ANTIGRAVITY_BUILD_DATE` for the timestamp. Two failure modes map to two
  functions to patch: "could not find `main-<hash>.js`" → `find_bundle_name`;
  "DOCS_STRUCTURE not found" → `parse_structure`.

#### `write-agent-skill`
- **What.** The skill-authoring *method* — a guide for writing new Agent Skills.
- **Why.** It is the **generator that precedes Layer 1's output**: the three doc
  experts were written *using* it. Encoding the method first, then stamping out
  experts, is the pattern that repeats in Layers 2 and 3.
- **Key files.** `.claude/skills/write-agent-skill/SKILL.md` (thin pointer),
  `references/extend-claude-with-skills.md` (300+ lines of official skill-authoring docs).
- **Depends on.** Nothing at runtime; it is reference material.
- **Gotchas.** `SKILL.md` intentionally holds almost nothing — the substance is
  in the `references/` file, loaded on demand (the same lazy-load philosophy).

### Layer 2 — Concept alignment

#### `concept-mapping`
- **What.** Read-only knowledge base answering "how does concept X map across
  Claude Code, Codex, and Antigravity?" One file per concept.
- **Why.** Three separate doc experts each mind their own turf; none remembers
  how the three line up. This fills that gap so learning transfers by *precise*
  analogy, not guesswork — and records the conclusion so nobody re-stitches it.
- **Key files.** `.claude/skills/concept-mapping/SKILL.md`; `ref/00-context-index.md`
  (navigational rollup); detail files `ref/01-project-prompt.md`,
  `02-project-settings.md`, `03-skills.md`, `04-custom-commands.md`, `05-hooks.md`,
  `06-mcp-servers.md`, `07-subagents.md`, `08-permissions.md`.
- **Depends on.** `Read`. Its facts were sourced from the Layer 1 skills.
- **Gotchas.** **Index first, then the detail file** — never answer a mapping
  question from memory when a detail file exists. Do not add facts here by hand;
  that is the builder's job.

#### `concept-mapping-builder`
- **What.** Authors and maintains the `concept-mapping` files against a fixed
  standard.
- **Why.** Concept files must all read as if one author wrote them (same column
  order, terminology, sourcing discipline). A builder-with-a-standard guarantees
  that; hand-writing would drift. Generator-before-output again.
- **Key files.** `.claude/skills/concept-mapping-builder/SKILL.md`;
  `ref/mapping-file-standard.md` (the authoritative shape); `ref/concept-file-template.md`.
- **Depends on.** `Read`, `Write`, `Edit`, `WebFetch`, `Skill` (it calls the
  Layer 1 doc skills to source every cell).
- **Gotchas.** **Detail file first, index second, always.** Claude Code is the
  seed column (frames the vocabulary). No blank cells — use `No equivalent` +
  context. Every non-obvious claim must be traceable to a doc page in a `Sources`
  section (URLs in raw `.md` form).

##### Design choice worth internalizing — "Porting-in notes" avoid N² blow-up
Each concept table's **last row is `Porting-in notes`**, organized **by
destination, not by direction**: one cell per tool answering "what bites when
someone else's config arrives *at this tool*". Three tools → three cells,
regardless of how many migration directions exist. Migration pain lives on the
receiving end, so keying notes to the destination collapses N×(N−1) directions
down to N. (See `ref/mapping-file-standard.md`.)

### Layer 3 — Migration

#### `port-skill-generator`
- **What.** Stamps out both a `port-<source>-to-<target>` (doer) and a
  `port-<source>-to-<target>-checker` (auditor) from two templates.
- **Why.** 12 near-identical files hand-maintained would drift the instant you
  fix one and forget another. One generator + two templates = single source of
  truth. Third repetition of generator-before-output.
- **Key files.** `.claude/skills/port-skill-generator/SKILL.md`;
  `ref/port-skill-template.md`; `ref/checker-skill-template.md`.
- **Depends on.** `Read`, `Write`, `Edit`. `disable-model-invocation: true`
  (run it explicitly, e.g. `/port-skill-generator cc to cdx`).
- **Gotchas.** The **agent roster is hardcoded** (adding a 4th tool is rare) but
  the **concept list is not** — templates never bake a concept list; generated
  skills read it fresh from `concept-mapping/ref/00-context-index.md` each run.
  Placeholders: `{{SOURCE_NAME}}`, `{{TARGET_NAME}}`, `{{SOURCE_SLUG}}`,
  `{{TARGET_SLUG}}`, `{{SOURCE_DOCS_SKILL}}`, `{{TARGET_DOCS_SKILL}}`,
  `{{PORT_SKILL_NAME}}`, `{{CHECKER_SKILL_NAME}}`. Verify no `{{` survives a run.

#### The 12 generated `port-*` skills
- **What.** Six directions, each a **doer + checker** pair:
  `port-antigravity-to-claude-code`(+`-checker`), `port-antigravity-to-codex`,
  `port-claude-code-to-antigravity`, `port-claude-code-to-codex`,
  `port-codex-to-antigravity`, `port-codex-to-claude-code`.
- **Why the doer/checker split.** So the tool that performed a migration never
  grades its own homework — the checker is read-only and independent.
- **Key files.** Each is a generated `.claude/skills/<name>/SKILL.md`.
- **Depends on.** Doer: `Read, Write, Edit, Glob, Grep, Skill`. Checker:
  `Read, Write, Glob, Grep, Skill` (its *only* write is the report).
- **Gotchas.** The checker writes exactly one file: `tmp/review-<port-skill-name>.md`
  with a fixed structure (Summary counts + a `Gaps` section per concept:
  present-on-source / state-on-target / what's-missing / suggested-change /
  priority). It never modifies project config. **Do not hand-edit any of the 12**
  — edit the templates and regenerate.

### Supporting / peripheral components
- **`.agents/skills/` mirror.** `claude-code-docs`, `codex-docs`,
  `antigravity-docs` are mirrored to the tool-neutral `.agents/skills/` path so
  Codex/Antigravity can discover them too. (See `concept-mapping/ref/03-skills.md`
  for why the neutral path exists.)
- **`chinese-english-punctuation`, `markdown-style`.** Doc-hygiene skills used

- **The `lesson-smith-*` family.** The course-authoring framework that generated
  this very teaching layer (including `lesson-smith-learn-this-project-meta`,
  which produced the `docs/learn-this-project/` docs and the six
  `learn-this-project-*` skills you may be reading this through).

## Conventions

- **Every skill is a folder with a `SKILL.md`** whose YAML frontmatter carries
  `name`, `description` (front-loaded with trigger keywords), often
  `allowed-tools`, `argument-hint`, and sometimes `disable-model-invocation`.
  Example: `.claude/skills/claude-code-docs/SKILL.md`.
- **Deny-by-default tools.** Skills request only the tools they need — read-only
  skills (`concept-mapping`) get `Read`; generators get `Write`/`Edit`.
- **Generator-before-output, three times.** Any place with many similar outputs
  has a single generator + template(s): `write-agent-skill`,
  `concept-mapping-builder` + `mapping-file-standard.md`, `port-skill-generator`
  + two templates.
- **Never from memory.** Layer 1 re-reads live docs; Layer 2 cites `Sources`;
  Layer 3 re-reads the concept index. "Fresh, not cached" is the house rule.
- **Bilingual docs.** English `README.md` / `docs/0X-*.md` are the canonical
  publishable versions; `-cn.md` counterparts are teaching aids (and get deleted
  before publishing — see `07-publish-checklist.md`).
- **`VERSION` + `CHANGELOG.md`** live inside each shipped doc skill.

## External dependencies

- **`WebFetch` (Claude Code built-in).** Layer 1's fetch mechanism. Chosen over a
  scraper because official docs expose raw `.md`, so no HTML parsing is needed.
- **`llms.txt` convention.** The machine-readable site index Layer 1 depends on.
  Verified (per `examples/02`) to be a real, widely-adopted public standard
  before being built on — not assumed.
- **`curl`/`urllib` (in `build_manifest.py`).** Used *instead of* `WebFetch` for
  the Antigravity JS bundle specifically, because `WebFetch` strips `<script>`
  tags and the doc map lives in the script.
- **`httpx2` (`pyproject.toml`).** Present as project scaffolding; not central to
  the skills' runtime behavior. `WHY (best guess; verify with project owner):`
  leftover from the Python-package skeleton `uv`/`mise` set up.
