# 这个 repo 到底要干一件什么事

## 1. coding agent 表面写代码, 骨子里是凌驾于一切技能之上的那个技能

先把一件容易被误解的事说清楚. coding agent 这个名字里带着 coding 两个字, 很容易让人把它归档成一个程序员的工具, 一门垂直技能, 跟不写代码的人没什么关系. 这恰恰是这整个 repo 要纠正的误读. coding agent 之所以能写代码, 是因为它本质上是一套通用的反馈循环: 给它一个目标, 它拆解, 执行, 检查结果, 再调整, 一轮一轮地收敛到答案. 写代码只是这套循环恰好落地的第一个领域, 因为写代码这件事本身几乎不需要额外工具, 一个文本编辑器就够了, 所以它是最容易验证, 最先跑通的场景.

但这套循环本身跟代码没有任何必然关系. 只要给它接上对应领域的工具, 它在那个领域里一样起飞:

* 科学研究里的实验设计和数据分析
* 文科类的资料整理和文献综述
* 临床医学场景里帮医生写 doctor note
* 自媒体场景里剪视频, 做音乐

这里有一个点, 让它跟你能学的任何其他技能都不一样. 其他所有技能都是**横向**的, 只让你在某一个领域里更强, 到此为止. 而这一门是**纵向凌驾于所有领域之上**的: 学好了它, 你就能套上任何领域的工具, 去做任何领域的事, 因为 agent 能. 它是这个时代里唯一一个凌驾于所有其他知识之上的知识, 一门以"其他一切技能"为回报的元技能. 所以如果你还只是把 coding agent 当成程序员专属的工具, 你已经站在了下一节要讲的那道代差的错误一侧.

---

## 2. 两三代的代差

正因为这一门技能凌驾于其他所有技能之上, 会不会用它就不再是技术岗位的加分项, 而是任何岗位都会被拉开差距的分水岭. 这里有一条推理链, 值得你现在就记下来, 后面几篇会反复用到它: agent 的能力上限, 在你用得足够好的前提下, 几乎是无限的, 因为它可以套上任何领域的工具, 去做任何领域的事. 反过来想, 如果你想让自己变得无限强, 你不需要在每个领域都亲自变强, 你只需要深度掌握 agent 这件事本身, 你就间接掌握了 agent 所能掌握的一切.

所以跨过这道门槛的人, 不是在某一门技能上领先一点点. 他的学习速度, 他消化和加工信息的质量, 他在团队内部精确传递信息的效率, 以及他整体的产出, 全都会跟没跨过这道门槛的人拉开**两三代**的代差. 而所谓"深度掌握 agent", 不是会打几个提示词, 而是知道怎么让它自己学会一件新事情, 怎么让它自己造出解决一个从没见过的新问题的能力. 这正是这个 repo 要教的东西, 也正是面试官问你"你平时到底怎么用 AI"时, 真正想探的: 表面问的是一个使用习惯, 底层要确认的是, 你整个思维模型是不是已经在 AI 时代重新搭建过.

---

## 3. 这门课不教你知识, 教你一套三层的解决问题的方法

那"让 agent 自己教自己"作为一种习惯, 具体长什么样? 它是一套三层的, 对付任何问题的打法, 我把它叫做**无限递归解决问题**.

* **第一层, 把问题直接丢给 AI.** 最普通的做法: 把问题原样交给 agent, 让它照着题目的表面去解答. 有时候这就够了, 也没什么不对.
* **第二层, 先造出专家, 再让专家来解.** 更高明的做法: 不直接去解这个问题. 先用 agent 去*鉴别*这个问题到底是什么, 然后造一个专门解决这一整类问题的超级专家 agent, 让*那个专家*去解. 你已经不是在解一个问题, 而是在造那个能解决所有同类问题的东西.
* **第三层, 造一个能造专家的 agent.** 有时候你连那个专家都还造不出来. 那就再退一步, 造一个专门用来造专家 agent 的 agent, 也就是学会亲手把那个"造专家的东西"搓出来.

为什么停在三层就够了? 因为这三层之间已经覆盖了所有情况. 任何问题, 要么被直接解掉 (第一层), 要么被你造的专家解掉 (第二层). 如果你造出来的专家*还是*解不了, 那这个问题就基本是不可解的了, 但请注意, 这个结论是你*真的把专家造出来*换来的, 不是拍脑袋猜的. 而当你连专家都造不出来时, 你就落到第三层, 去造那个造专家的东西. 原则上它还能继续往下, 第四层, 第五层, 但你很少需要把递归说到那么深, 关键在于, 一个问题永远可以再往下拆一层. 这就是为什么这套习惯叫*无限递归解决问题*: 你永远不会撞到死胡同, 你只是再往下递归一层, 直到退到某个你能亲手造出来的东西, 再一层层装配回去.

这个 repo 活在第二层和第三层. 想想一个普通老师: 你问, 他答一次, 下次你又回到原点. 第二层的做法, 是造一个专门教这一件事的专家 agent, 24 小时随时在, 永远不会不耐烦, 也永远不会过时. 这个 repo 里的三个文档 Skill 就是这样三个专家, 分别对应 Claude Code, Codex, Antigravity. 但这个 repo 真正的目标是第三层, 它不是把三个现成的专家塞给你, 而是教你自己去造一个. 所以你最后拿走的, 从来不是"Claude Code 怎么用"这种注定会过时的事实, 而是那个底层技能: "当一个工具在我脚下不断变化时, 我怎么造一个能跟它保持同步, 持续教我的专家". 这是造专家的方法, 不是某一个专家.

---

## 4. 三个已经造出来的专家, 作为例子, 外加一个预告, 这个模式会跑四次

这套造专家的方法, 目前已经在三个 coding agent 身上跑通, 分别是 `claude-code-docs`, `codex-docs`, `antigravity-docs`, 对应 Claude Code, Codex, Antigravity. 三个专家各自负责发现和读取自己那个工具的官方文档, 能回答安装, 认证, 配置, 命令, 工作流, 自动化, 排错, 进阶用法这些问题, 而且依据永远是当前版本的官方文档, 不是训练数据里的旧印象. 三个工具的文档组织方式不一样, 所以三个专家内部的实现也不完全相同, 这留到下一篇讲. 现在你只需要抓住这一点: 这三个是这套方法造出来的三个例子, 不是这套方法的全部, 你完全可以用同样的方法给第四个, 第五个工具造新专家.

有一件事值得现在就埋下, 因为它正是最后一篇要兑现的. 这个递归动作在这个 repo 里不是只出现一次, 而是**四**次, 一层套一层. 造文档专家 (第一层) 本身就是一次完整的递归. 第二层也是. 第三层也是. 然后这三层*合起来*, 把第三层的目标当作真正的终点, 又构成一次更大的递归, 而它的子步骤恰好就是第一, 二, 三层. 三次内层递归, 全被包在第四次, 更大的那次里面: 你可以把它记成 **1 + 3**, 一个总的大拆解, 由三个小拆解搭起来, 同一个模式的四个实例. 我们不急着四个一起讲. 我们从第一个开始, 造一个专家, 从这里把你引出来.

---

## 5. 这只是故事的第一层

如果这个 repo 到此为止, 它顶多是三个做得比较讲究的专家 agent. 但事情并没有到此为止: 在这三个专家之上, 这个 repo 还搭了两层能力, 一层用来对齐不同 agent 之间同一个概念的对应关系, 一层用来真正执行, 把一个项目的配置从一个 agent 迁移到另一个 agent. 这三层加在一起, 才是这个 repo 真正想让你看到的东西, 也是下一篇要拆开讲的内容, 就是我们刚刚预告的四次递归里的第一次.

而能把造专家这件事从头到尾想清楚, 并且真的做出来的人, 已经拿到了第 2 节那条推理链的钥匙: 你不需要在每个领域里都变得无限强, 你只需要深度掌握 agent, 你就间接掌握了它所触及的一切. 这句话现在听起来可能还有点抽象, 后面几篇会把它落到实处.
