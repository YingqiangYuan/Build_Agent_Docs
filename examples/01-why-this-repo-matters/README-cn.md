# 这个 repo 到底要干一件什么事

## 1. coding agent 表面写代码, 骨子里是一个万能生产力引擎

先把一件容易被误解的事说清楚. coding agent 这个名字里带着 coding 两个字, 很容易让人以为它只是一个写代码的工具, 跟程序员之外的人没什么关系. 事实完全不是这样. coding agent 之所以能写代码, 是因为它本质上是一套反馈循环: 给它一个目标, 它拆解, 执行, 检查结果, 再调整, 一轮一轮地收敛到答案. 写代码只是这套反馈循环恰好落地的第一个领域, 因为写代码这件事本身几乎不需要额外的工具, 一个文本编辑器就够了, 所以它是最容易验证, 最先跑通的场景.

但这套反馈循环本身跟代码没有必然关系. 只要给它接上对应领域的工具, 它就能在那个领域里一样起飞:

* 科学研究里的实验设计和数据分析
* 文科类的资料整理和文献综述
* 临床医学场景里帮医生写 doctor note
* 自媒体场景里剪视频, 做音乐

这些事情跟敲代码没有任何关系, 但对 agent 来说, 只是换了一套工具而已, 反馈循环本身完全通用. 所以如果你只把 coding agent 当成一个程序员专属的工具, 你已经在被后面要讲的那种代差甩下的路上了, 因为它真正的身份, 是任何行业, 任何专业都能用的通用生产力引擎.

---

## 2. 两三代的代差

正因为这个引擎是通用的, 会不会用它就不再是一个技术岗位的加分项, 而是任何岗位都会被拉开差距的分水岭. 一旦你跨过这道门槛, 学会把日常工作流定义成 Agent Skill, 给 agent 造工具, 把它接进自己的文件系统和习惯里, 你的学习速度, 你消化和加工信息的质量, 你在团队内部精确传递信息的效率, 以及你整体的生产力, 都会跟没跨过这道门槛的人产生两三代的代差.

这里有一条推理链, 值得你现在就记下来, 后面几篇还会反复用到它: agent 的能力, 在你用得足够好的前提下, 几乎是无限的, 因为它可以套上任何领域的工具, 去做任何领域的事. 反过来想, 如果你想让自己变得无限强, 你不需要每个领域都亲自变强, 你只需要深度掌握 agent 这件事本身, 你就间接掌握了 agent 所能掌握的一切. 而怎么才算深度掌握 agent, 不是会打几个提示词, 而是知道怎么让它自己学会一件新事情, 自己造出解决新问题的能力. 这正是这个 repo 要教的东西.

也正因为这样, 企业招聘的时候会开始专门考察这件事. 面试官问你 "你平时怎么用 AI 的", 表面上是在了解一个使用习惯, 底层想确认的其实是: 你的思维模型, 你的认知框架, 是不是已经在 AI 时代重新搭建过, 你是不是已经养成了以终为始, 把问题无限拆解, 再逐层交给合适的角色去解决的本能.

---

## 3. 这门课不教你知识, 教你造一个教你的专家

普通的老师是什么样子. 你有一个具体问题, 想学一个具体的东西, 老师来教你, 教完这一次, 下一次你有新问题, 还得回去找老师, 或者重新自己摸索.

更厉害一层的老师会这么做: 与其每次都亲自教你, 不如直接帮你造一个专门教这件事的专家 agent, 这个专家 agent 24 小时不间断, 随时可以问, 永远不会不耐烦, 而且知道的东西不会因为老师个人的记忆而过时. 这已经是很厉害的一层了, 这个 repo 里的三个文档 Skill, 就是这样三个专家 agent, 分别是 Claude Code, Codex, Antigravity 各自的专家.

但这个 repo 真正想教你的, 是比这更高的一层: 它不是直接把这三个专家 agent 塞给你就完事, 而是教你怎么自己去造一个这样的专家 agent. 也就是说, 这门课教的从来不是 "Claude Code 怎么用" 这种会过时的具体知识, 而是 "遇到一个会持续变化的工具, 我怎么造一个能一直跟它保持同步的专家 agent 出来教我" 这件事本身. 学会了这一层, 你面对的就不再是三个工具, 而是任意一个工具, 任意一个会变化的知识领域, 因为你手上握着的是造专家的方法, 不是某一个专家.

---

## 4. 三个已经造出来的专家, 作为例子

这套造专家的方法, 目前已经在三个 coding agent 身上跑通, 分别是 `claude-code-docs`, `codex-docs`, `antigravity-docs`, 对应 Claude Code, Codex, Antigravity. 三个专家各自负责发现和读取自己那个工具的官方文档, 能回答安装, 认证, 配置, 命令, 工作流, 自动化, 排错, 进阶用法这些问题, 而且回答的依据永远是当前版本的官方文档, 不是训练数据里的旧印象.

三个工具的文档组织方式并不一样, 所以三个专家内部的实现细节也不完全相同, 这一点留到下一篇拆开讲. 这一篇你只需要记住: 这三个只是这套方法造出来的三个例子, 不是这套方法的全部, 你完全可以用同样的方法, 给任何第四个, 第五个工具, 造一个新的专家出来.

---

## 5. 这只是故事的第一层

如果这个 repo 到此为止, 它顶多是三个做得比较讲究的专家 agent. 但事情并没有到此为止: 在这三个专家之上, 这个 repo 还搭了两层能力, 一层用来对齐不同 agent 之间同一个概念的对应关系, 一层用来真正执行, 把一个项目的配置从一个 agent 迁移到另一个 agent. 这三层加在一起, 才是这个 repo 真正想让你看到的东西, 也是下一篇要拆开讲的内容.

而能把造专家这件事从头到尾想清楚, 做出来的人, 已经拿到了那条推理链的钥匙: 你不需要在每个领域里都变得无限强, 你只需要深度掌握 agent, 你就间接掌握了它的一切. 这句话现在听起来可能还有点抽象, 后面几篇会把它落到实处.
