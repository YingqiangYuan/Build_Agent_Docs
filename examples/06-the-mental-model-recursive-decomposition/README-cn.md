# 撑住这整个故事的思维模型

## 1. 跳出这个 repo, 看看撑住整个故事的到底是什么

前五篇一直在这一个 repo 里打转: 为什么值得学, 第一层怎么造出来, 怎么收拢成一个面试故事, 二三层的底层实现, 追问怎么接. 这一篇要做一件不一样的事, 跳出这个 repo, 把撑住整个故事的那套思维模型单独摘出来看, 说清楚它不是只对这一个 repo 管用的技巧.

如果这套思维模型只能用来讲这一个故事, 它的价值就封顶在这一个故事上. 真正值钱的地方, 是它能原样搬到任何一个跟 Claude Code, 跟这个 repo 毫无关系的问题上, [上一篇](../05-answering-follow-up-questions/README-cn.md) 结尾已经露了两次这种搬家, 这一篇要把搬家背后那条通用的规则讲透, 然后在最后, 告诉你在面试里*用*这一切的两种具体打法.

---

## 2. 这套思维模型到底是什么, 无限递归拆解

名字听起来抽象, 拆开看其实是几个很具体的动作, 一步一步来, 就是[第一篇](../01-why-this-repo-matters/README-cn.md) 开篇那三层阶梯:

* 先问自己真正要的终点是什么, 不是眼前这一步, 是最后落地的那个目标.
* 问能不能直接, 可靠地把这个终点造出来. 能, 就直接造, 事情到此结束. (这就是第一层, 直接丢给 agent.)
* 不能, 别自己一层一层手动去啃, 而是退一步问, 能不能造一个机制, 一个专家, 让它持续, 可靠地产出这个终点. (第二层.)
* 如果连这个专家本身都造不出来, 再退一步, 问能不能造一个专门用来造这个机制的机制. (第三层.)
* 一路退, 退到某一步真的能直接动手造为止, 这一步就是地基.
* 地基造好之后, 反过来一层一层往上装配: 用最底下这层, 造出上一层, 再用上一层, 造出再上一层, 一直装配回最初那个终点.

这就是 "以终为始" 加上 "递归" 的完整意思: 以终为始负责决定倒着退到哪一步该停, 递归负责说明, 退一步之后遇到的, 其实是同一个问题的缩小版, 用的是同一套追问, 只是规模变小了.

---

## 3. 这套模型在这个 repo 里跑了四次, 也就是 "1 + 3"

[第一篇](../01-why-this-repo-matters/README-cn.md) 埋下了这个种子, 并且承诺在这里兑现: 同一个递归动作在这个 repo 里不是只出现一次, 而是**四**次, 小的一次套在大的一次里面. [第二篇](../02-building-the-first-expert/README-cn.md) 和[第四篇](../04-building-layers-two-and-three/README-cn.md) 已经把这四次都具体走过了:

* 它在**第一层内部**走了一次: 终点是一个不会过时的 Claude Code 专家, 退一步造出 `write-agent-skill` 这个会写 Skill 的方法, 再用它造出 `claude-code-docs`.
* 它在**第二层内部**再走一次: 终点是一份可靠的概念对齐知识库, 退一步造出 `concept-mapping-builder`, 再用它造出 `03-skills.md` 这样的具体对齐文件.
* 它在**第三层内部**又走一次: 终点是十二个不走样的迁移工具, 退一步造出 `port-skill-generator`, 再用它套出十二个具体的 Skill.
* 然后**三层拼起来**, 从头到尾又走了一次, 而且是更大的一次: 终点是企业级的跨 agent 迁移能力, 倒推出需要第三层, 第三层倒推出需要第二层, 第二层倒推出需要第一层.

这就是 **1 + 3**: 三次内层递归 (每层一次), 全被包在一次更大的递归里面, 而这次大递归的子步骤, 恰好就是那三层. 同一套追问, 用在了四种不同的尺度上, 小的套在大的里面. 发现一个模式用了一次不算什么, 发现它在同一件事里反复地, 一层套一层地出现, 才说明真的抓住了这套模型的骨架, 而不是记住了一个巧合.

## 4. 为什么这不是这个 repo 的专利

[上一篇](../05-answering-follow-up-questions/README-cn.md) 已经主动搬过两次家: 一次搬到内容追踪, 一次搬到跟 Claude Code 毫无关系的团队敏捷培训, 造一个人均一个的 Scrum Master 专家. 两次搬家用的是同一套追问, 换的只是终点和落地的那一步.

能这样搬家, 是因为这套模型认的不是 "Claude Code", 也不是 "coding agent", 它认的是三种更抽象的情形: 终点会不断变化, 直接记住答案迟早过时; 终点前面有大量几乎相同, 只是细节不同的重复劳动, 手工维护迟早走样; 或者直接造终点这件事太大, 但造一个持续产出终点的机制, 规模反而可控. 这三种情形几乎存在于任何行业, 任何规模的问题里, 这也是为什么[第一篇](../01-why-this-repo-matters/README-cn.md) 开篇要先讲清楚, coding agent 本身就是那个凌驾于一切技能之上的技能. 这套思维模型正是驾驭这项元技能的方式, 而不是这项技能本身的某个功能.

## 5. 在面试里到底怎么用这一切, 两种打法

上面讲的都是这套模型为什么重要, 这一节讲的是怎么把它兑现成钱. 一旦你真的把这套能力内化了, 你手上握着的就不是 "我会 Claude Code", 而是一种通用能力: **解决任何问题, 学会任何领域, 随时成为一个领域专家.** 面试里最难的, 是怎么*证明*这一点, 而大多数人恰恰栽在这里. 先诚实面对一个约束: 任何一场面试里, 你的时间和精力都有限, 你不可能对面试官可能提到的一切都是面面俱到的专家. 很多人会说 "我学得很快", 但一个没有证据支撑的说法是立不住的. 整个博弈的核心, 是给面试官留下一个*被证明过*的印象: 这个人能学会任何知识, 能快速成为任何领域的专家, 能拆解并解决任何问题. 有两种情形可以把它兑现, 而这两种几乎覆盖了所有情况.

### 打法 A, 他问到一个你已经很熟的技能或领域

准备工作要放在面试*之前*做: 挑一个你本来就很熟的技能, 刻意用这套方法把它重新过一遍, 端到端地重新推导, 亲手把这个技能的专家搓出来 (走一遍 discover, verify, encode, test). 那么当面试官提到这个技能时, 你就不只是回答问题, 而是把它展开: "我给你看看我当时是怎么学会这个的." 你自然而然地把这套能力引出来, 然后讲一个真实的故事: 我第一次用这套方法, 就是我马上要给你看的这个 repo; 从那以后我用它学了无数其他技能, 而你刚刚问我的这个, 刚好就是我用一模一样的方法拆解过的. 面试官看到的, 是你既学会了这个技能, 又把这套方法搬到了另一个领域上. 他被留下的那个结论才是值钱的: 以后任何你还没遇到过的领域, 技能, 问题, 你都能搞定. 普通候选人最怕的就是那个念头, "万一他问到我不懂的怎么办", 只能退回到 "我会很快学会", 却没有任何东西撑腰. 而你已经当场撑住了, 有证据, 所以面试官根本不会再担心你学不学得会新东西.

> 有一条边界是从[第三篇](../03-the-interview-story/README-cn.md) 沿用下来的: 你放到屏幕上给人看的, 永远是你造出来的那个**真实, 能跑的 Skill** (在 `.claude/skills/` 下), 绝不是 `examples/` 这个教学文件夹. 你展示的是你亲手做出来的成品, 不是你学它的那份教程.

### 打法 B, 他问到一个你完全不懂的领域

这里你同样可以把这套东西拿出来. 直接说: "这个具体的东西我现在还不懂, 但我大概知道它是什么, 而且我有信心能搞定, 因为我有一套 AI native 的, 快速成为任何领域专家的方法", 然后把这套方法给他过一遍. 你留下的印象在形状上是一样的: 这场面试一结束, 你就会把这套方法对准这个话题, 把它拆解, 学会, 变成那个专家, 于是你*此刻*不懂这件事本身, 就不再是一个减分项了. 面试官会觉得非常踏实, 因为你把 "我不懂 X" 重新框成了 "我有一套可靠的流程, 能让自己学会任何一个 X".

### 甚至他压根没问你一个具体问题的时候

把这两种合起来看. 他问到你懂的领域, 你就秀肌肉, 并且在同一个动作里*证明*你是个货真价实的 quick learner. 他问到你不懂的领域, 你还是把这套方法拿出来, 传达那个唯一重要的信号: 给我一点时间, 我什么都能搞定. 而当他压根没问你一个具体的技术问题, 只是一个 behavioral question, 想看看你这个人怎么样的时候, 你依然可以传达同样的东西, 不是靠打嘴炮说自己怎么样, 而是靠*展示*. 把你亲手造出来的真实成品调出来给人看, 有视觉冲击力, 而且是有证据的, 它落地的力度比一个候选人干巴巴地说 "我学东西很快" 要强上好几个数量级. 这个点很长, 但它就是你该带走的那个点: 在面试里, 这套能力不是你用来*描述*的, 而是你用来*展示*的.

## 6. 回到第一篇开篇那句话, 这才是真正被考察的东西

[第一篇](../01-why-this-repo-matters/README-cn.md) 提过, 企业招聘专门考察 "用 AI 能力", 底层想确认的是, 一个人的思维框架是不是已经在 AI 时代重新搭建过. 现在可以把这句话说得更精确: 真正被考察的, 就是眼前这套无限递归拆解的能力, 遇到终点会变化, 会重复, 会大到无从下手的问题, 第一反应是不是去问 "我该造一个什么样的机制", 而不是卷起袖子自己手动做一遍.

会用 AI 写代码, 只证明会用一个工具. 看得懂这套追问, 能在任意一个新问题上重新走一遍, 并且像第 5 节讲的那样, 能随时把它*展示*出来, 证明的是另一件完全不同的事: 这个人已经把 AI 时代的思维框架长在了自己身上. 这也是[第三篇](../03-the-interview-story/README-cn.md) 讲稿里那句 "我用 AI 的方式叫做无限递归解决问题" 真正想立住的论点.

## 7. 学完这六篇, 真正要做的是把它变成自己的

六篇读完, 如果只是记住了这个 repo 三层架构叫什么名字, 这六篇就白读了. 真正要做到的, 是把这整套发现, 验证, 编码, 测试, 以及一层套一层的以终为始, 也就是那个 1 + 3, 内化成自己遇到任何问题时的第一反应, 甚至到了能在面试里坦然说出 "这是我自己做的" 的地步, 而不是复述一份别人写好的案例.

能在面试里把这套东西当场讲清楚, 接住追问, 像[上一篇](../05-answering-follow-up-questions/README-cn.md) 里那样主动举一反三, 而且最重要的, 能用第 5 节那两种打法把它*展示*出来, 这件事本身就是最有力的证明: 证明这个人用 AI 的习惯和思维模型, 已经能让他面对任何行业, 任何规模的问题, 都无限级地拆解下去, 一路拆到能落地的一步, 再一层层装配回来. 对面的人感受到的, 不会是 "这个人会用 Claude Code", 而是这个人的 AI 能力几乎是无限的, 这正是[第一篇](../01-why-this-repo-matters/README-cn.md) 开篇那条推理链, 走到这里, 真正兑现的地方.
