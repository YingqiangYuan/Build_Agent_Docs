# 撑住这整个故事的思维模型

## 1. 跳出这个 repo, 看看撑住整个故事的到底是什么

前五篇一直在这一个 repo 里打转: 为什么值得学, 第一层怎么造出来, 怎么收拢成一个面试故事, 二三层的底层实现, 追问怎么接. 这一篇要做一件不一样的事, 跳出这个 repo, 把撑住整个故事的那套思维模型单独摘出来看, 说清楚它不是只对这一个 repo 管用的技巧.

如果这套思维模型只能用来讲这一个故事, 它的价值就封顶在这一个故事上. 真正值钱的地方, 是它能原样搬到任何一个跟 Claude Code, 跟这个 repo 毫无关系的问题上, [上一篇](../05-answering-follow-up-questions/README-cn.md) 结尾已经露了两次这种搬家, 这一篇要把搬家背后那条通用的规则讲透.

---

## 2. 这套思维模型到底是什么, 无限递归拆解

名字听起来抽象, 拆开看其实是几个很具体的动作, 一步一步来:

* 先问自己真正要的终点是什么, 不是眼前这一步, 是最后落地的那个目标.
* 问能不能直接, 可靠地把这个终点造出来. 能, 就直接造, 事情到此结束.
* 不能, 别自己一层一层手动去啃, 而是退一步问, 能不能造一个机制, 让它持续, 可靠地产出这个终点.
* 如果连这个机制本身都造不出来, 再退一步, 问能不能造一个专门用来造这个机制的机制.
* 一路退, 退到某一步真的能直接动手造为止, 这一步就是地基.
* 地基造好之后, 反过来一层一层往上装配: 用最底下这层, 造出上一层, 再用上一层, 造出再上一层, 一直装配回最初那个终点.

这就是 "以终为始" 加上 "递归" 的完整意思: 以终为始负责决定倒着退到哪一步该停, 递归负责说明, 退一步之后遇到的, 其实是同一个问题的缩小版, 用的是同一套追问, 只是规模变小了.

---

## 3. 这套模型在这个 repo 里, 出现的不止一次

[第二篇](../02-building-the-first-expert/README-cn.md) 和[第四篇](../04-building-layers-two-and-three/README-cn.md) 已经具体走过这套模型, 而且不是走了一次:

* 第一层内部走了一次: 终点是一个不会过时的 Claude Code 专家, 退一步造出 `write-agent-skill` 这个会写 Skill 的方法, 再用它造出 `claude-code-docs`.
* 第二层内部再走一次: 终点是一份可靠的概念对齐知识库, 退一步造出 `concept-mapping-builder`, 再用它造出 `03-skills.md` 这样的具体对齐文件.
* 第三层内部又走一次: 终点是十二个不走样的迁移工具, 退一步造出 `port-skill-generator`, 再用它套出十二个具体的 Skill.
* 三层拼起来, 从头到尾又走了一次, 而且是更大的一次: 终点是企业级的跨 agent 迁移能力, 倒推出需要第三层, 第三层倒推出需要第二层, 第二层倒推出需要第一层.

同一套追问, 用在了四种不同的尺度上, 小的套在大的里面. 发现一个模式用了一次不算什么, 发现它在同一件事里反复地, 一层套一层地出现, 才说明真的抓住了这套模型的骨架, 而不是记住了一个巧合.

---

## 4. 为什么这不是这个 repo 的专利

[上一篇](../05-answering-follow-up-questions/README-cn.md) 已经主动搬过两次家: 一次搬到内容追踪, 一次搬到跟 Claude Code 毫无关系的团队敏捷培训, 造一个人均一个的 Scrum Master 专家. 两次搬家用的是同一套追问, 换的只是终点和落地的那一步.

能这样搬家, 是因为这套模型认的不是 "Claude Code", 也不是 "coding agent", 它认的是三种更抽象的情形: 终点会不断变化, 直接记住答案迟早过时; 终点前面有大量几乎相同, 只是细节不同的重复劳动, 手工维护迟早走样; 或者直接造终点这件事太大, 但造一个持续产出终点的机制, 规模反而可控. 这三种情形几乎存在于任何行业, 任何规模的问题里, 这也是为什么[第一篇](../01-why-this-repo-matters/README-cn.md) 开篇要先讲清楚, coding agent 本身就是一个能装进任何领域的通用生产力引擎, 这套思维模型正是驾驭这台引擎的方式, 而不是这台引擎本身的某个功能.

---

## 5. 回到第一篇开篇那句话, 这才是真正被考察的东西

[第一篇](../01-why-this-repo-matters/README-cn.md) 提过, 企业招聘专门考察 "用 AI 能力", 底层想确认的是, 一个人的思维框架是不是已经在 AI 时代重新搭建过. 现在可以把这句话说得更精确: 真正被考察的, 就是眼前这套无限递归拆解的能力, 遇到终点会变化, 会重复, 会大到无从下手的问题, 第一反应是不是去问 "我该造一个什么样的机制", 而不是卷起袖子自己手动做一遍.

会用 AI 写代码, 只证明会用一个工具. 看得懂, 而且能在任意一个新问题上重新走一遍这套追问, 证明的是这个人已经把 AI 时代的思维框架长在了自己身上, 这也是[第三篇](../03-the-interview-story/README-cn.md) 讲稿里那句 "我用 AI 的方式叫做无限递归解决问题" 真正想立住的论点.

---

## 6. 学完这六篇, 真正要做的是把它变成自己的

六篇读完, 如果只是记住了这个 repo 三层架构叫什么名字, 这六篇就白读了. 真正要做到的, 是把这整套发现, 验证, 编码, 测试, 以及一层套一层的以终为始, 内化成自己遇到任何问题时的第一反应, 甚至到了能在面试里坦然说出 "这是我自己做的" 的地步, 而不是复述一份别人写好的案例.

能在面试里把这套东西当场讲清楚, 接住追问, 甚至像[上一篇](../05-answering-follow-up-questions/README-cn.md) 里那样主动举一反三, 这件事本身就是最有力的证明: 证明这个人用 AI 的习惯和思维模型, 已经能让他面对任何行业, 任何规模的问题, 都无限级地拆解下去, 一路拆到能落地的一步, 再一层层装配回来. 对面的人感受到的, 不会是 "这个人会用 Claude Code", 而是这个人的 AI 能力几乎是无限的, 这正是[第一篇](../01-why-this-repo-matters/README-cn.md) 开篇那条推理链, 走到这里, 真正兑现的地方.
