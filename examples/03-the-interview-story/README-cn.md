# 一个能在面试里讲出来的故事

## 1. 从一句 "你平时怎么用 AI" 说起

面试里迟早会有人问到这句话, 或者它的某个变体: 你平时怎么用 AI 的, 举个例子看看. 这句话看起来随意, 但它是一个筛子.

大部分人的第一反应是往下沉的答案: 我用它写代码, 我用它查资料, 我用它改改文案. 这些答案都对, 但都在往下沉, 因为它们说的是 AI 帮你干了一件具体的活, 而没有说出你和 AI 之间到底是什么关系. [上一篇](../02-building-the-first-expert/README-cn.md) 已经摊开讲过一个具体例子, 这一篇要做的是把那个例子收拢成一个能在这一刻拿出来讲的故事.

---

## 2. 故事不是架构总览, 是一次造专家的完整过程

一个常见的误区是, 觉得故事应该讲这个 repo 有多大, 分了几层, 每一层叫什么名字. 这种讲法听起来像是在背一份架构文档, 面试官很难当场判断你是真的做过, 还是复述了一遍别人写的说明.

真正能站住的故事, 是[上一篇](../02-building-the-first-expert/README-cn.md) 里那一次具体, 完整, 从头走到尾的经历: 打开 Claude Code 的官方文档, 注意到一个不起眼的 Copy page 按钮, 顺着复制下来的内容里一句提示, 找到了整个网站的文档索引 `llms.txt`, 没有直接信它, 先让 Claude 联网确认这是不是一个被官方认可的可靠机制, 确认之后才用 [`write-agent-skill`](../../.claude/skills/write-agent-skill/SKILL.md) 把这套发现写成了 [`claude-code-docs`](../../.claude/skills/claude-code-docs/SKILL.md) 这个 Skill, 又拿从没读过的页面去测试它, 确认它真的管用. 这一件事, 从头到尾都是自己亲手走过的, 面试官问哪一步, 都答得出来, 这才是能立住的故事, 而不是一份让人半信半疑的总览.

---

## 3. 故事的骨架, 发现, 验证, 编码, 测试

这次经历之所以经得起讲, 是因为它天然带着一个清晰的骨架, 四个动作, 一个都不能少:

* 发现一个别人没太注意的细节, 一个按钮, 一句提示
* 不急着信它, 先去验证这个细节背后是不是一个真实, 可靠, 会一直存在的机制
* 把验证过的机制写成一套可以重复调用的规则, 而不是一次性用完就丢
* 拿新的, 没见过的情况去测试, 确认它真的立得住

讲这个故事的时候, 这四步就是天然的段落, 面试官顺着听下来, 会觉得这个人做事有章法, 而不是随手试了一下运气好. 这个骨架也不只是这一个故事专属的, 后面几篇还会反复用到它.

---

## 4. 为什么这个故事能证明 "用 AI 能力"

[第一篇](../01-why-this-repo-matters/README-cn.md) 里讲过一条推理链: agent 的能力几乎无限, 深度掌握 agent, 就间接掌握了它能掌握的一切, 而深度掌握不是会打几个提示词, 是知道怎么让它自己学会一件新事情. 这次经历正好是这条推理链的一次完整落地: 没有人把 Claude Code 的用法喂给你, 你自己发现了它文档背后的机制, 验证了它, 把它变成了一个会一直保持新鲜的专家, 而且这套流程本身可以原样用在任何一个第三方工具上, 不限于 Claude Code.

面试官问 "你平时怎么用 AI", 表面是问一个使用习惯, 实际是想知道你和 AI 之间的关系是主动的还是被动的. 讲完这个故事, 答案已经很清楚: 你不是在被动等 AI 给你答案, 你在教它怎么替你持续产出答案, 而且你知道怎么验证它靠不靠谱. 这正是那条推理链要证明的东西, 也是这个考察项真正想看到的东西.

---

## 5. 讲的时候, 故意不要讲什么

这个故事最容易讲垮的方式, 是讲着讲着把整个 repo 的架构都端出来, 主动提到还有第二层专门对齐不同工具之间的概念, 第三层专门做迁移. 这样做只会稀释故事, 让一个具体的经历变成一份不完整的架构介绍, 听起来像是在赶着展示自己知道的多, 而不是在讲一件真的做过的事.

讲这个故事的时候, 刻意只讲这一个专家是怎么造出来的, 把二, 三层留着不主动说. 这不是因为你还没吃透二, 三层, 后面会花专门一篇把它们讲透, 到时候你是真的懂. 刻意不说的原因是: 主动一次性把所有细节倒出来, 反而不像是真懂, 更像是背了一份稿子. 让对方自己顺着问下去, 你再一层一层接得住, 这个过程本身才是在向对方证明, 你脑子里真的是 AI native 的思维方式, 面对任何深度的追问都能自然地往下拆, 而不是提前把话都说完.

---

## 6. 故事讲完, 你已经站在了哪里

讲完这个故事, 你已经不是在回答一个 "怎么用 AI" 的问题, 而是在展示一套做事方法: 观察, 验证, 固化, 检验. 这套方法这次用在了给 Claude Code 造一个文档专家上, 但它显然不是只能用在这一件事上.

这个故事讲得越扎实, 越容易引来更深的追问, 这些追问该怎么接, 是接下来要准备的内容.

---

## 7. 现场怎么说, 一份可以照着讲的讲稿

前面讲的都是道理, 真到了面试现场, 得有一段能直接开口说的话. 不是每场面试都能分享屏幕, 能分享的时候, 按下面旁白里写的去操作; 不能分享的时候, 把旁白部分跳过, 靠嘴把那句话说清楚就够了, 自己灵活处理. 还有一条界线要记住: 能拿出来给面试官看的, 只有 `.claude/skills/` 底下真正在跑的 Skill 本身, 不要把 `examples/` 这个教程目录露出来, 这里是你练故事的地方, 不是故事的素材.

开场这一句话最重要, 它定了整段话的调子:

> 我用 AI 的方式, 叫做 infinite recursive problem solving, 中文讲就是无限递归地解决问题. 做法是无限地 working backward, 从目标往回拆, 一直拆到能落地的那一步, 再一步一步做上去.

> 举个例子, 当我要用 AI 解决一个问题的时候, 我的第一步不是自己动手去解决它, 而是先去造一个能解决这个问题的超级 Agent, 再用这个 Agent 去解决问题. 如果我发现自己造不出这个 Agent, 我就退一步, 去造一个能造出这个 Agent 的 Agent.

> 拿一个我真做过的例子来说. 有一次我需要一个专家, 能随时告诉我 Claude Code 最新的用法, 但 Claude Code 更新得很快, 我不想造一个知识会过时的专家.

*(如果可以分享屏幕: 打开 Claude Code 官方文档的 Quickstart 页面, 也就是 https://code.claude.com/docs/en/quickstart, 让对方看到这是官方在线文档, 不是你自己整理的笔记)*

> 我去翻它的官方文档, 注意到页面右上角有一个 Copy page 按钮.

*(如果可以分享屏幕: 点一下 Copy page, 把复制出来的内容念给对方听开头那几行, 或者直接贴出来给对方看)*

> 复制下来的内容开头有一句提示, 说整个网站有一份完整的文档索引, 叫 llms.txt.

*(如果可以分享屏幕: 打开 https://code.claude.com/docs/llms.txt, 让对方看一眼这份索引长什么样)*

> 我把这份索引抓下来一看, 整个网站几百个页面全被压成了一份平铺的列表, 每一条都能直接换成一次干净的抓取. 我没有直接信它, 先让 Claude 联网确认, llms.txt 是不是一个被广泛采用, 官方认可的公开约定, 而不是这一个网站自己临时搞出来的东西. 确认下来是真的, 我才动手, 用 write-agent-skill 把这套发现的机制写成了一个 Skill.

*(如果可以分享屏幕: 最后打开这个仓库, 定位到 [`.claude/skills/claude-code-docs/SKILL.md`](../../.claude/skills/claude-code-docs/SKILL.md), 让对方看到刚才说的这一整套机制, 现在是一个真实存在, 会被调用的文件, 不是一张截图或者一页 PPT, 顺手滚动到 Procedure 部分, 指给对方看那条一次读 1 到 3 页, 最多读 9 页的规则)*

> 我在这个 Skill 里定义了一条具体的规则: 每次只批量读 1 到 3 页, 读完先判断够不够回答问题, 不够就再读下一批, 最多读到 9 页还是不够, 就诚实地停下来, 告诉对方读到了什么, 缺什么, 问要不要继续, 而不是把整个网站读一遍浪费 token. 写完之后我拿了几个完全没读过的页面去测试, 确认它每次都能定位到对的那一页, 给出有依据的回答.

> 现在这个 Skill 就是我随身带着的 Claude Code 专家, 它不会过时, 因为它每次都现读官方文档, 而不是背我教它的某个版本的答案. 但这个专家本身还不是终点, 我带着它去做真正的事情的时候, 会不断撞到新问题, 每撞到一个, 就再迭代一次, 让它变得更准. 真正值钱的不是这一个专家, 而是我现在已经知道怎么造这种专家了, 以后遇到任何一个会变化的工具, 任何一个新问题, 我都可以照着这条路子, 再造一个新的专家出来解决它. 这就是我说的无限递归解决问题: 我没有自己去啃 Claude Code 的用法, 我造了一个会自己保持新鲜的专家, 而且我知道怎么继续造下去.

*(旁白: 讲到这里故意停一下, 留一个钩子. 这一路只讲了一个专家是怎么造出来的, 如果对方顺着问, 那你造出来的这些专家会不会打架, 或者你怎么把一个配置从一个 agent 搬到另一个 agent 上, 那就是在问第二, 三层, 到时候再接着往下讲)*

这份讲稿到这里就结束了, 而且刻意只停在第一层. 真实经历里, 支撑这一整套系统的还有另外两层, 一层负责让不同 agent 之间的概念对得上号, 一层负责真正把配置从一个 agent 搬到另一个 agent, 这两层是怎么被造出来的, 下一篇会用同样的办法, 一步一步摊开来讲.
