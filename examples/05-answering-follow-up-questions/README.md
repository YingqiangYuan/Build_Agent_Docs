# The Interviewer Pushes Back: How Do You Respond?

## 1. Picking Up the Thread from Last Time

The pitch in [Part 3](../03-the-interview-story/README.md) ended on a deliberate cliffhanger: it only covered the first layer, and just hinted that layers two and three existed without ever unpacking them. [Part 4](../04-building-layers-two-and-three/README.md) filled in the full implementation of those two layers. This piece is about connecting those two threads: if the interviewer actually takes the bait and asks the follow-up, how do you answer.

A follow-up question isn't a problem, it's an opportunity. The more restrained the original pitch, the more curious the interviewer gets, and the questions that curiosity produces almost always fall into a handful of predictable buckets. The first four are questions you answer defensively, each one starts by naming exactly what the interviewer is really testing, then gives you a response you can deliver verbatim, none of it invented on the spot, all of it pulled straight from facts already established in [Part 1](../01-why-this-repo-matters/README.md), [Part 2](../02-building-the-first-expert/README.md), and [Part 4](../04-building-layers-two-and-three/README.md). The last two are different: instead of waiting to be asked, you go on offense and volunteer an extra step, proving this way of thinking isn't just a script memorized for one specific repo.

---

## 2. Follow-up One: How Exactly Do These Three Layers Work?

This question is testing whether the story actually holds up under pressure, or whether it was just architecture-speak that falls apart the moment someone digs in. The point of the answer isn't to recite the names of the three layers again, it's to spell out the concrete action each layer performs, and how the layers relate to each other.

> Layer one reads the official documentation index fresh every single time, it never relies on a memorized answer. Using Claude Code as the example, that's the Skill I described earlier. Layer two lines up the same concept across all three tools, using the concept of a "skill" itself as the example: Claude Code keeps skills under `.claude/skills/`, while Codex and Antigravity keep them under `.agents/skills/`. That mapping gets written down as a single reference document, and even that document isn't written from memory, it's only committed to paper after going back and asking the three layer-one experts. Layer three actually carries out or reviews a migration, and none of the twelve migration Skills it uses were written by hand, they were generated by running one generator against two templates, and every time it runs, it goes back and asks layer two for the current list of concepts. All three layers share one rule: no layer ever copies the layer below it and welds it into place, everyone always asks fresh.

## 3. Follow-up Two: What Happens When an Agent Changes Its Documentation Structure?

This question is testing whether the whole system is a piece of brittle manual work that shatters at the first change, or whether it was designed from day one with change in mind. This is exactly the problem the three layers have been built to handle from the start, so the answer doesn't need to be improvised, it's already baked in.

> Layer one is barely affected, because it never caches documentation content, it fetches the index fresh every time. As long as the index itself still exists, it doesn't matter which page got renamed or moved, the next read picks it up automatically. Layer two takes a localized hit: if a tool's actual behavior changes, you just rerun the maintenance process for that one concept, ask the three experts again for the current answer, and update only that single document, nothing else needs to be touched. Layer three is almost never affected, because it never knows the specific concepts involved in the first place, it just reads layer two's current list at runtime, so when layer two updates, layer three follows automatically. The one genuinely painful scenario is a tool ripping out its entire discovery mechanism, say it stops publishing an index file at all, in which case you'd have to redo the discovery-and-verification process from scratch. But that's a low-probability event, and even then you'd be running the exact same method.

## 4. Follow-up Three: Do These Skills Conflict with Each Other, or Duplicate Work?

This question is testing basic architectural judgment, whether you know how to draw clean lines of responsibility instead of ending up with a pile of features tripping over each other.

> No, they don't, because each layer only owns its own responsibility. Layer one is only responsible for discovering and reading documentation, it doesn't decide how concepts line up, and it doesn't execute any migration. Layer two is only responsible for aligning concepts, it doesn't invent its own conclusions, and it doesn't touch a single file in a migration. Layer three is only responsible for executing or reviewing a migration, it doesn't invent new concept mappings, it only reads what layer two has already written. Layer three even deliberately splits into two roles internally: one that actually changes files, and one that only reads and checks whether the change is complete, then writes up a report. That way the one doing the editing never gets to grade its own homework.

## 5. Follow-up Four: What Did You Actually Do in All This, or Did You Just Let the AI Handle Everything?

This is the most important question, and it's the one [Part 3](../03-the-interview-story/README.md) flagged as worth leaving for the interviewer to ask on their own. It's testing whether you actually drove everything just described, or whether you typed a few prompts and left the rest to luck.

> The AI genuinely did a huge amount of the hands-on work: crawling documentation, writing the Skills, running the tests, all of that was its execution. But the moments where real decisions got made were mine. First, noticing that the unassuming "Copy page" button was worth digging into, instead of scrolling right past it. Second, finding `llms.txt` and refusing to just trust it, insisting on verifying first whether it was a genuinely recognized, widely adopted mechanism. Third, making the same call at all three layers: don't build the final thing you actually want directly, build a mechanism that keeps producing it instead. I made that call three separate times, the AI didn't come up with that design on its own. Fourth, when designing the aligned knowledge base, choosing to write migration reminders organized by destination rather than by direction, which headed off a combinatorial explosion before it started. These are architectural decisions. The AI was responsible for executing them well, but the decisions themselves were mine. That's exactly what I mean by solving a problem through infinite recursion: I was the one breaking the problem down at every step and deciding what needed to get built next, rather than handing the whole problem to the AI untouched.

## 6. Follow-up Five: Go on Offense, Show How This Method Applies to Tracking Content

Once the first four questions are answered, the story already stands on its own. This is the point where you don't wait to be asked again, you volunteer the next step yourself. [Part 1](../01-why-this-repo-matters/README.md) opened by claiming that a coding agent can be applied to any domain. Here's a chance to make good on that claim with an example that has nothing to do with Claude Code, proving this isn't a script memorized for one repo.

> This method isn't limited to building documentation experts. Say, for example, I wanted to automatically track the latest papers or news in some field every day and generate a daily digest. I'd use the exact same approach: first check whether that information source publishes its own machine-readable index, something like `llms.txt`, most serious sources do. Once you find it, don't trust it blindly, verify first whether it's a stable, officially sanctioned mechanism. Once confirmed, turn that discovery process into a Skill that fetches the latest entries fresh every time, instead of me manually checking every day. Then test it against a few topics it's never seen before, to confirm it's actually pulling accurate results. It's the exact same skeleton used to build the Claude Code expert, just pointed at a completely unrelated domain, and it still works.

## 7. Follow-up Six: One More Demonstration, Turning Agile Training into a Scrum Master for Every Team Member

The second offensive example shifts to something closer to team management, and has nothing to do with coding agents at all, proving this method can even handle a purely organizational problem like "teach an entire team something."

> Here's another example closer to team management. Plenty of teams in North America run agile development on Jira, but not everyone on the team actually understands Scrum. The traditional fix is either relying on one scarce human Scrum Master, or running a few training sessions that everyone forgets a few weeks later, with no way to get a question answered on the spot. I'd apply the same method: instead of teaching everyone myself, and instead of expecting one human Scrum Master to be everywhere at once for everybody, I'd start by finding the authoritative, stable sources on Scrum itself, things like the official Scrum Guide, plus Jira's own agile documentation, and verify carefully that these are actually reliable, authoritative references. Then I'd turn that discovery process into a Scrum Master expert Skill, so that every person on the team has their own version they can ask anytime, and the answer always reflects current best practice, not whatever was on a slide deck from some training session months ago. This is the same exact thing as building an expert for Claude Code, just this time the expert is teaching not a coding agent, but how to do Scrum correctly.

## 8. Once You've Answered These, Follow-up Questions Don't Scare You Anymore

The first four questions look like they're probing architecture, stability, boundaries, and ownership respectively, but every answer grows naturally out of the same material you've already fully internalized, none of it needs to be improvised on the spot. The last two aren't defensive, they're bonus points, proving this way of thinking works just as well applied to content tracking as it does to team management, regardless of whether the tool underneath is Claude Code or Jira. The follow-up question that actually makes people nervous is the kind that forces you to invent an answer you've never considered before, and here, every single answer is either a fact already nailed down in [Part 1](../01-why-this-repo-matters/README.md), [Part 2](../02-building-the-first-expert/README.md), and [Part 4](../04-building-layers-two-and-three/README.md), or a line of reasoning you'd already worked out, just applied to a different scenario.

Handling the follow-up well means the cliffhanger left at the end of [Part 3](../03-the-interview-story/README.md) did its job, it filtered for exactly the kind of interviewer who actually knows the subject. From here, it's time to step outside this repo entirely and look at what kind of thinking actually underlies this whole ability to tell the story, field the follow-ups, and even volunteer extensions of your own, and where else that thinking applies, in problems that have nothing to do with this repo at all.
