# 面试官追问了, 该怎么接

## 1. 从上一次留的钩子说起

[第三篇](../03-the-interview-story/README-cn.md) 的讲稿结尾, 故意留了一个钩子: 只讲了第一层, 把第二, 三层的存在露了个口风, 但没有展开. [第四篇](../04-building-layers-two-and-three/README-cn.md) 把这两层的底层实现完整补上了. 这一篇要做的, 是把这两件事接起来: 如果面试官真的顺着钩子问下去了, 该怎么接.

追问不是麻烦, 是机会. 故事讲得越克制, 面试官越容易好奇, 而好奇心问出来的问题, 大概率就是接下来这几种. 前四问是被动接招, 每一种都先说清楚对方到底想考察什么, 再给一段可以直接照讲的回答, 这段回答不是新编的, 全部来自[第一篇](../01-why-this-repo-matters/README-cn.md), [第二篇](../02-building-the-first-expert/README-cn.md), [第四篇](../04-building-layers-two-and-three/README-cn.md) 已经讲过的事实. 后两问不一样, 是主动出击, 不等对方问, 自己往上加一步, 证明这套思路不是只在这一个 repo 里现学的话术.

---

## 2. 追问一, 这三层具体是怎么运作的

这个问题在考的是, 故事是不是真的立得住, 还是只在架构层面滑了一下, 一细问就露馅. 回答的重点不是重新背一遍三层的名字, 而是能不能把每一层的具体动作说清楚, 而且说出层与层之间的关系.

> 第一层, 每次都现读官方的文档索引, 不背旧答案, 拿 Claude Code 举例, 就是我之前讲的那个 Skill. 第二层, 把同一个概念在三个工具里的样子对齐, 拿 skill 这个概念本身举例, Claude Code 的 skill 放在 `.claude/skills/`, Codex 和 Antigravity 放在 `.agents/skills/`, 这份对照关系写成一份文件, 而且这份文件也不是凭印象写的, 是回头问第一层的三个专家才落笔的. 第三层, 真正去执行或者审查一次迁移, 而且这十二个迁移用的 Skill 不是手写的, 是用一个生成器套两份模板生成出来的, 生成出来之后, 每次运行还会回头问第二层要最新的概念清单. 三层连起来, 有一条共同的规矩: 每一层都不把下一层的东西抄一份焊死在自己身上, 永远现问.

---

## 3. 追问二, 如果某个 agent 改了文档结构怎么办

这个问题在考的是, 这套东西是不是一碰就碎的手工活, 还是设计的时候就想过会变化这件事. 这恰好是三层从第一天就在应对的问题, 答案早就在里面, 不用现编.

> 第一层不会受太大影响, 因为它从来不缓存文档内容, 每次都现抓索引, 只要那份索引本身还在, 具体哪一页改了名字, 挪了位置, 下一次现读就自动跟上了. 第二层会受局部影响, 如果某个工具的行为真的变了, 只需要针对那一个概念重新跑一遍维护流程, 回头问三个专家拿最新的答案, 只改这一份文件, 不用碰其他概念. 第三层几乎不会受影响, 因为它从来不知道具体有哪些概念, 只在运行的时候现读第二层的清单, 第二层更新了, 它自动就跟着更新. 真正麻烦的情况, 是一个工具把整套发现机制换掉了, 比如不再提供索引文件, 那就要重新走一遍发现, 验证的过程, 但这属于小概率事件, 而且走的还是同一套方法.

## 4. 追问三, 这些 Skill 之间会不会互相冲突, 或者重复劳动

这个问题在考的是有没有基本的架构意识, 知不知道怎么把职责边界画清楚, 而不是一堆功能互相踩脚.

> 不会, 因为每一层只认自己那一份职责. 第一层只负责发现和读取文档, 不判断概念怎么对齐, 也不执行迁移. 第二层只负责对齐概念, 不自己编结论, 也不动手迁移任何文件. 第三层只负责执行或者审查迁移, 不发明新的概念对照关系, 只读第二层已经写好的. 第三层内部还刻意分了两个角色, 一个真的去改文件, 一个只读地检查改得全不全, 写一份报告, 这样负责改的那个不会既当运动员又当裁判员自己给自己打分.

---

## 5. 追问四, 你自己在这个过程里做了什么, 还是完全让 AI 代劳

这是最关键的一问, 也是[第三篇](../03-the-interview-story/README-cn.md) 提醒过要留给对方主动问的问题. 它在考的是, 前面讲的这一切, 到底是你在主导, 还是你只是敲了几行提示词, 剩下的全靠运气.

> AI 确实动手做了大量具体的活, 抓文档, 写 Skill, 跑测试, 这些都是它执行的. 但几个真正拿主意的时刻, 是我自己的判断: 第一, 注意到 Copy page 这个不起眼的按钮值得深挖, 而不是划过去. 第二, 找到 llms.txt 之后没有直接信它, 坚持先验证它是不是一个被广泛认可的机制. 第三, 在三层里都做了同一个决定, 不直接造最终想要的东西, 而是先造一个能持续产出它的机制, 这个决定我做了三次, 不是 AI 自己想到要这样设计. 第四, 在设计对齐知识库的时候, 选了按目的地写迁移提醒, 而不是按方向写, 提前避开了组合爆炸. 这些是架构决定, AI 负责把决定执行到位, 但决定本身是我做的, 这正是我说的无限递归解决问题, 一路都是我在拆解问题, 定下每一步该造什么, 而不是把整个问题原封不动地丢给 AI.

## 6. 追问五, 主动秀一次, 这套方法搬到内容追踪上

前四问答完, 故事已经立住了, 这时候不用等对方再问, 可以自己往上加一步. [第一篇](../01-why-this-repo-matters/README-cn.md) 开篇就说过, coding agent 能用在任何领域, 这里正好拿一个跟 Claude Code 毫无关系的例子, 把这句话兑现给对方看, 证明这不是一套只对这一个 repo 现学的话术.

> 这套方法不是只能用在文档专家上. 打个比方, 如果我想每天自动追踪某个领域最新的论文或者新闻, 生成一份简报, 我会用同一套思路: 先去找这个信息源自己有没有一份机器可读的索引, 类似 llms.txt 那种东西, 大部分严肃的信息源都有. 找到之后不直接信, 先验证它是不是一个稳定, 官方认可的机制. 确认了, 才把这套发现写成一个 Skill, 让它每次都现抓最新的条目, 而不是我自己每天去翻. 写完拿几个没见过的主题去测试, 确认它抓得准. 跟造 Claude Code 专家用的是同一套骨架, 换了一个完全不相关的领域, 一样能走通.

## 7. 追问六, 再秀一次, 把敏捷培训直接做成人均一个的 Scrum Master

第二个主动出击的例子, 换一个更贴近团队管理, 而且完全不涉及 coding agent 本身的场景, 证明这套方法连 "教会一整个团队一件事" 这种纯管理问题都能接住.

> 再举一个更贴近团队管理的例子. 北美很多团队用 Jira 做敏捷开发, 但团队里不是每个人都真的懂 Scrum, 传统做法要么靠一个稀缺的人类 Scrum Master, 要么搞几次培训, 培训完过一阵子就忘了, 而且没法随时答疑. 我会用同一套方法: 不是自己去逐个教, 也不是指望一个人类 Scrum Master 分身乏术地满足所有人, 而是先去找 Scrum 本身权威, 稳定的源头, 比如官方的 Scrum Guide, 加上 Jira 自己的敏捷文档, 验证清楚这些是不是靠谱的权威说法, 再把这套发现写成一个 Scrum Master 专家 Skill, 让团队里每个人手上都有一个自己的, 随时能问, 而且答案永远贴着当前的最佳实践, 不是某次培训 PPT 里过时的说法. 这跟给 Claude Code 造专家是同一件事, 只是这次专家教的不是一个 coding agent, 而是怎么把 Scrum 做对.

## 8. 这几问答完, 你已经不怕追问了

前四问看起来分别在问架构, 稳定性, 边界, 归属, 但答案全都从同一套已经吃透的东西里自然长出来, 不需要现场编. 后两问不是防守, 是加分项, 证明这套思路能落到内容追踪, 也能落到团队管理, 跟具体用的是 Claude Code 还是 Jira 完全无关. 真正让人紧张的追问, 是那种要现编一个从没想过的说法, 而这里的每一个回答, 都是[第一篇](../01-why-this-repo-matters/README-cn.md), [第二篇](../02-building-the-first-expert/README-cn.md), [第四篇](../04-building-layers-two-and-three/README-cn.md) 里已经写死的事实, 或者已经想清楚的思路, 换了个场景而已.

追问接得住, 说明[第三篇](../03-the-interview-story/README-cn.md) 结尾留的那个钩子没有白留, 它筛出来的正是懂行的面试官. 接下来要跳出这个 repo 本身, 看看这一整套讲故事, 接追问, 甚至主动举一反三的能力, 背后到底是什么思维方式在撑着, 以及它能用在哪些跟这个 repo 完全无关的问题上.
